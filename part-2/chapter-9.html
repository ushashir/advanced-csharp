Exceptions — When Plans Go Wrong

No matter how carefully you write code, things will go wrong at runtime — files will be missing, networks will time out, users will enter invalid data. Exceptions are C#'s structured system for detecting and handling these unexpected situations without crashing the entire program.

What you'll learn in this chapter

  • The try/catch/finally pattern and how it works
  • How to throw exceptions with throw new Exception()
  • How to create your own custom exception classes
  • The exception class hierarchy in .NET
  • When NOT to use exceptions
  • The difference between Exception and SystemException
  • A real-world file-reading example with proper exception handling
🔥 The Fire Alarm Analogy

Think of exception handling like a building's fire alarm system. When everything is fine, the alarm is silent and everyone goes about their work. The moment something goes wrong — a fire, a gas leak — the alarm activates. It immediately stops normal activity, alerts the relevant people, and triggers a specific, pre-planned response.

In C#, a thrown exception is the alarm. The catch block is the fire warden with a response plan. The finally block is the action that happens regardless — opening the exit doors, logging the incident — whether the alarm was real or a drill.

Try, Catch, Finally

The three keywords work together. Code inside try runs normally. If an exception is thrown inside try, execution jumps immediately to the matching catch block. The finally block always runs, whether or not an exception occurred — perfect for cleanup work like closing files or database connections. 

try
{
    // Normal code that might fail
    int result = 10 / 0;   // DivideByZeroException thrown here
    Console.WriteLine(result);   // never reached
}
catch (DivideByZeroException ex)
{
    // Handle specifically DivideByZeroException
    Console.WriteLine($"Caught: {ex.Message}");
}
catch (Exception ex)
{
    // Catch-all for any other exception
    Console.WriteLine($"Unexpected error: {ex.Message}");
}
finally
{
    // Always runs — even if no exception occurred
    Console.WriteLine("Cleanup complete.");
}
💡 Catch Most Specific First

Always put the most specific catch blocks before the most general. The CLR checks catch blocks from top to bottom and uses the first one that matches. If you put catch (Exception ex) first, it will catch everything and the specific handlers below it will never run. The compiler will warn you about this.

Throwing Exceptions

You can throw exceptions deliberately from your own code when input or state is invalid. This communicates the problem clearly to the caller: 

public class AgeValidator
{
    public static void Validate(int age)
    {
        if (age < 0)
            throw new ArgumentOutOfRangeException(nameof(age),
                "Age cannot be negative.");

        if (age > 150)
            throw new ArgumentOutOfRangeException(nameof(age),
                "Age seems unrealistically high.");
    }
}

// Usage
try
{
    AgeValidator.Validate(-5);
}
catch (ArgumentOutOfRangeException ex)
{
    Console.WriteLine(ex.Message);
    // Age cannot be negative. (Parameter 'age')
}

The nameof(age) expression returns the string "age" — it is safer than a string literal because it will update automatically if you rename the parameter, and the compiler checks that the name exists.

Common Built-In Exception Types

  • ArgumentNullException — a required argument was null
  • ArgumentOutOfRangeException — a numeric argument was outside the valid range
  • ArgumentException — general argument problem (base class for the above)
  • InvalidOperationException — the operation is not valid in the current state
  • NotSupportedException — the operation is not supported at all
  • NotImplementedException — stub for code not yet written
  • NullReferenceException — accessing a member on a null reference (usually a bug)
  • KeyNotFoundException — key not found in a dictionary
  • FileNotFoundException — file does not exist
  • IOException — general I/O error (file, network)
  • OverflowException — arithmetic overflow in a checked context
  • DivideByZeroException — integer division by zero
  • FormatException — input string was not in the expected format

Creating Custom Exceptions

When the built-in exceptions do not describe your problem precisely, create your own. A custom exception class inherits from Exception (or a more specific subclass): 

// Convention: exception class names end in "Exception"
public class NotFoundException : Exception
{
    public string ResourceType { get; }
    public string ResourceId  { get; }

    public NotFoundException(string resourceType, string resourceId)
        : base($"{resourceType} with id '{resourceId}' was not found.")
    {
        ResourceType = resourceType;
        ResourceId   = resourceId;
    }
}

public class OrderService
{
    private readonly Dictionary<string, string> _orders = new()
    {
        { "ORD-001", "iPhone 15" }
    };

    public string GetOrder(string orderId)
    {
        if (!_orders.TryGetValue(orderId, out var order))
            throw new NotFoundException("Order", orderId);

        return order;
    }
}

// Usage
var service = new OrderService();
try
{
    var order = service.GetOrder("ORD-999");
}
catch (NotFoundException ex)
{
    Console.WriteLine(ex.Message);
    // Order with id 'ORD-999' was not found.
    Console.WriteLine($"Resource type: {ex.ResourceType}");
}

The Exception Hierarchy

Every exception in .NET ultimately inherits from System.Exception. The two main branches are:

System.Exception ├── System.SystemException ← Thrown by the runtime itself │ ├── NullReferenceException │ ├── IndexOutOfRangeException │ ├── DivideByZeroException │ ├── StackOverflowException │ └── OutOfMemoryException └── System.ApplicationException ← Intended for application-level errors └── (your custom exceptions)
📚 Should I inherit ApplicationException?

The original .NET design intended ApplicationException to be the base for all user-defined exceptions, and SystemException for runtime exceptions. However, Microsoft's own guidelines now say: just inherit directly from Exception. The distinction was never enforced, and ApplicationException adds no value. Modern C# code ignores it.

File Reading with Proper Exception Handling

Here is a real-world example: reading a configuration file with full exception handling and guaranteed cleanup using finally: 

using System.IO;

public static string? ReadConfigFile(string filePath)
{
    StreamReader? reader = null;
    try
    {
        reader = new StreamReader(filePath);
        string content = reader.ReadToEnd();
        Console.WriteLine($"Read {content.Length} characters from {filePath}");
        return content;
    }
    catch (FileNotFoundException ex)
    {
        Console.WriteLine($"Config file not found: {ex.FileName}");
        return null;
    }
    catch (UnauthorizedAccessException)
    {
        Console.WriteLine("Permission denied — cannot read config file.");
        return null;
    }
    catch (IOException ex)
    {
        Console.WriteLine($"I/O error reading config: {ex.Message}");
        return null;
    }
    finally
    {
        // Always close the reader — even if an exception was thrown
        reader?.Dispose();
        Console.WriteLine("File reader disposed.");
    }
}
💡 Use the using Statement Instead

For resources that implement IDisposable (like StreamReader), C# provides the using statement, which automatically calls Dispose() when the block exits — even if an exception is thrown. It is much cleaner than manual finally blocks: 

using var reader = new StreamReader(filePath);
string content = reader.ReadToEnd();   // reader.Dispose() called automatically

When NOT to Use Exceptions

Exceptions are for exceptional situations — unexpected failures. Do not use them for normal control flow. This is a common mistake: 

// BAD — using exceptions for expected conditions
try
{
    int value = int.Parse(userInput);   // throws if invalid
    ProcessValue(value);
}
catch (FormatException)
{
    Console.WriteLine("Please enter a number.");
}

// GOOD — use TryParse instead
if (int.TryParse(userInput, out int value))
{
    ProcessValue(value);
}
else
{
    Console.WriteLine("Please enter a number.");
}

The second pattern is faster (no exception overhead), clearer, and follows the "Try" pattern that .NET uses throughout — int.TryParse, Dictionary.TryGetValue, Stack.TryPop, and so on. A user entering an invalid number is not an exceptional event — it is a perfectly normal thing to handle.

📚 Key Terms

Exception: An object that represents an error or unexpected event. All exceptions inherit from System.Exception.

try: A block containing code that might throw an exception.

catch: A block that handles a specific exception type if it is thrown in the corresponding try block.

finally: A block that always runs after try/catch — used for guaranteed cleanup.

throw: The keyword used to raise an exception: throw new ArgumentException("message").

Exception.Message: A human-readable description of what went wrong.

Exception.StackTrace: The call stack at the point the exception was thrown — invaluable for debugging.

Exception.InnerException: The original exception if this exception was thrown in response to another exception — used when wrapping exceptions.

Chapter Summary

  • try wraps code that might fail; catch handles specific exception types; finally always runs for cleanup.
  • Catch the most specific exception types first, then more general ones.
  • Use throw new ExceptionType("message") to signal errors from your own code.
  • Custom exceptions inherit from Exception directly (not ApplicationException).
  • The using statement automatically disposes IDisposable resources — prefer it over manual finally for resources.
  • Do not use exceptions for expected conditions — use TryXxx pattern methods instead.
  • SystemException is for runtime-thrown exceptions; your own exceptions should inherit Exception directly.
