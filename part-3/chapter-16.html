REST APIs — The Menu and the Waiter

REST APIs are how modern applications talk to each other. Your mobile app, your frontend, third-party services — they all communicate with your backend through a REST API. In this chapter, you will build a real one with ASP.NET Core controllers.

What you'll learn in this chapter

  • What REST is and why it became the standard for web APIs
  • HTTP verbs: GET, POST, PUT, DELETE, PATCH — and when to use each
  • HTTP status codes: 200, 201, 400, 404, 500 and what they mean
  • JSON as the universal data language of the web
  • Route templates, URL parameters, and query strings
  • Reading request bodies with [FromBody]
  • Returning IActionResult vs typed results
  • Swagger/OpenAPI for automatic API documentation
  • A complete Products API with GET, POST, and GET-by-id

The Restaurant Analogy

A REST API is like a restaurant. The menu is your list of endpoints — it tells clients what they can order (which routes are available and what data they return). The waiter is your controller — it takes the order (the HTTP request), brings it to the kitchen (your service layer), and returns the finished dish (the HTTP response) to the customer (the caller).

Just as a good restaurant menu is clear and consistent — starters, mains, desserts, each with a name and description — a well-designed REST API has consistent, predictable routes and responses. Customers know exactly what to expect.

🍽️ Menu and Waiter

GET /products → "Show me everything on the menu."
GET /products/42 → "I'd like dish number 42."
POST /products → "I'd like to add a new dish to the menu."
PUT /products/42 → "Please update dish 42 with these new details."
DELETE /products/42 → "Remove dish 42 from the menu."

Each response comes back with a status code on the ticket: ✓ 200 OK, ✓ 201 Created, ✗ 404 Not Found, ✗ 400 Bad Request, ✗ 500 Internal Server Error.

What REST Actually Means

REST stands for Representational State Transfer. It is an architectural style — a set of constraints — not a protocol or standard. An API that follows REST conventions is called "RESTful." The key principles are:

  • Stateless: every request from the client must contain all the information needed to process it. The server stores no session state between requests.
  • Resource-based: everything is modelled as a resource (a product, a user, an order) identified by a URL. /products/42 is the resource "product with ID 42."
  • Standard verbs: use HTTP verbs to describe the action — GET to read, POST to create, PUT/PATCH to update, DELETE to remove.
  • Uniform interface: consistent naming, consistent response shapes, consistent use of status codes.

HTTP Verbs and When to Use Them

  • GET — Read a resource. Must not change any data (idempotent). GET /products or GET /products/5.
  • POST — Create a new resource. The server decides the new ID. POST /products with the product data in the body.
  • PUT — Replace a resource entirely. You send the full updated object. PUT /products/5.
  • PATCH — Partially update a resource. You send only the fields that changed. PATCH /products/5.
  • DELETE — Remove a resource. DELETE /products/5.
📊 The Most Common HTTP Status Codes

2xx — Success: 200 OK (request succeeded), 201 Created (resource created, often with a Location header pointing to it), 204 No Content (success, nothing to return — common for DELETE).

4xx — Client error: 400 Bad Request (malformed input), 401 Unauthorized (not authenticated), 403 Forbidden (authenticated but not permitted), 404 Not Found (resource doesn't exist), 409 Conflict (e.g. duplicate creation), 422 Unprocessable Entity (valid JSON but fails validation).

5xx — Server error: 500 Internal Server Error (unhandled exception), 503 Service Unavailable (server is overloaded or down).

Creating Your First Controller

Controllers in ASP.NET Core are classes decorated with [ApiController] and [Route] attributes. Each public method with an HTTP verb attribute becomes an endpoint. 

using Microsoft.AspNetCore.Mvc;

namespace MyShop.Controllers;

[ApiController]
[Route("api/[controller]")]   // resolves to /api/products
public class ProductsController : ControllerBase
{
    // Simple in-memory list for demonstration
    private static readonly List<Product> _products = new()
    {
        new Product { Id = 1, Name = "Laptop",   Price = 1200.00m },
        new Product { Id = 2, Name = "Keyboard", Price =   89.99m },
        new Product { Id = 3, Name = "Monitor",  Price =  450.00m },
    };

    // GET /api/products
    [HttpGet]
    public ActionResult<IEnumerable<Product>> GetAll()
    {
        return Ok(_products);
    }

    // GET /api/products/1
    [HttpGet("{id:int}")]
    public ActionResult<Product> GetById(int id)
    {
        var product = _products.FirstOrDefault(p => p.Id == id);
        if (product is null)
            return NotFound(new { Message = $"Product {id} not found." });

        return Ok(product);
    }

    // POST /api/products
    [HttpPost]
    public ActionResult<Product> Create([FromBody] CreateProductRequest request)
    {
        var product = new Product
        {
            Id    = _products.Max(p => p.Id) + 1,
            Name  = request.Name,
            Price = request.Price
        };

        _products.Add(product);

        // 201 Created + Location header pointing to the new resource
        return CreatedAtAction(nameof(GetById), new { id = product.Id }, product);
    }
}

The Supporting Models

// Domain model — the full entity
public class Product
{
    public int     Id    { get; set; }
    public string  Name  { get; set; } = string.Empty;
    public decimal Price { get; set; }
}

// Request DTO — what the caller sends in the POST body
// We don't let the caller set the ID — the server assigns it
public class CreateProductRequest
{
    public string  Name  { get; set; } = string.Empty;
    public decimal Price { get; set; }
}

Route Templates and URL Parameters

// Route parameter — part of the URL path
[HttpGet("{id:int}")]       // matches /api/products/42
public IActionResult GetById(int id) { ... }

// Query string parameter — appended after ?
// matches /api/products/search?query=laptop&maxPrice=500
[HttpGet("search")]
public IActionResult Search(string query, decimal maxPrice = 9999m)
{
    var results = _products
        .Where(p => p.Name.Contains(query, StringComparison.OrdinalIgnoreCase)
                  && p.Price <= maxPrice)
        .ToList();
    return Ok(results);
}

// Route with multiple segments
[HttpGet("category/{category}/featured")]  // /api/products/category/electronics/featured
public IActionResult GetFeatured(string category) { ... }

IActionResult vs ActionResult<T>

You have two choices for return types in controller actions:

  • IActionResult — the most flexible. You can return Ok(), NotFound(), BadRequest(), etc. The downside: Swagger doesn't know what type the "success" response contains, so documentation is less rich.
  • ActionResult<T> — tells the compiler (and Swagger) the expected success type. You can still return error results, but when you return the success case, Swagger knows the response shape. 
// Prefer ActionResult<T> — gives Swagger better documentation
[HttpGet("{id:int}")]
public ActionResult<Product> GetById(int id)
{
    var product = _products.FirstOrDefault(p => p.Id == id);
    if (product is null) return NotFound();  // IActionResult (error)
    return product;                           // implicit Ok(product)
}

OpenAPI / Swagger

Swagger is a tool that reads your API and generates interactive documentation automatically. When you visit http://localhost:5000/swagger during development, you see every endpoint, its parameters, and can even send live test requests from the browser — no Postman needed. 

// In Program.cs — enable Swagger in development
builder.Services.AddEndpointsApiExplorer();
builder.Services.AddSwaggerGen();

var app = builder.Build();

if (app.Environment.IsDevelopment())
{
    app.UseSwagger();
    app.UseSwaggerUI();   // browse to /swagger
}
💡 [ApiController] Does a Lot For You

The [ApiController] attribute on your controller class enables several useful behaviours automatically: it performs model validation and returns a 400 Bad Request with a structured error body if validation fails (so you don't have to check ModelState.IsValid manually); it infers [FromBody] for complex types in POST/PUT actions; and it returns RFC 7807 "problem details" JSON for error responses, which is a standard format clients can rely on.

📚 Key Terms

REST: Representational State Transfer — an architectural style for designing networked APIs using standard HTTP verbs and resource-based URLs.

[ApiController]: An ASP.NET Core attribute that enables automatic model validation, binding inference, and structured error responses for a controller.

[Route]: Defines the URL prefix for all actions in a controller. [Route("api/[controller]")] uses the controller name as the segment.

[FromBody]: Tells ASP.NET Core to read the parameter value from the JSON request body, rather than from the URL or query string.

DTO (Data Transfer Object): A simple class used to define the shape of data sent to or from an API — often different from the internal domain model.

OpenAPI / Swagger: A specification for describing REST APIs in a machine-readable format. Swagger UI generates interactive documentation from this specification.

Chapter Summary

  • REST APIs use HTTP verbs (GET, POST, PUT, PATCH, DELETE) to describe operations on resources identified by URLs.
  • HTTP status codes communicate outcomes: 2xx for success, 4xx for client errors, 5xx for server errors. 201 Created is the correct response for a successful POST, not 200 OK.
  • JSON is the standard data format for REST APIs. ASP.NET Core serialises C# objects to JSON automatically.
  • Controllers are classes annotated with [ApiController] and [Route]. Each public method with an HTTP verb attribute becomes an endpoint.
  • Route parameters ({id:int}) capture values from the URL path. Query string parameters are method parameters that ASP.NET Core reads from ?key=value.
  • Use ActionResult<T> as the return type to give Swagger full visibility of your success response shape.
  • Swagger/OpenAPI generates live, interactive API documentation that you can use to test endpoints during development.
