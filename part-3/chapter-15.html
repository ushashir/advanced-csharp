Dependency Injection — The Supply Chain

Dependency Injection is one of those concepts that sounds intimidating until the moment it clicks — and then you wonder how you ever lived without it. ASP.NET Core has DI baked in at the very core, and understanding it deeply will make you a far better backend developer.

What you'll learn in this chapter

  • What dependency injection is and the problem it solves
  • Why DI leads to loosely-coupled, testable code
  • Constructor injection — the primary DI pattern in ASP.NET Core
  • The three service lifetimes: Transient, Scoped, and Singleton
  • Registering services in Program.cs with builder.Services
  • A real example: EmailService injected into a controller

The Supply Chain Analogy

Imagine a car factory. To build a car, the factory needs hundreds of components: tyres, engines, glass, electronics. A naive factory might decide to manufacture everything itself — spin up its own tyre plant, build its own glass furnace, design its own chips. This is a nightmare: enormously complex, hard to change, and impossible to test.

The smart approach is a supply chain. The factory decides what it needs and publishes a list of requirements. A logistics team (a supplier) fulfils those requirements and delivers the parts to the factory floor. The factory doesn't care where the tyres came from or how they were made — it just fits them. If you want to switch tyre suppliers, you change one contract, not the entire factory.

🏭 The Supply Chain

Your class (the factory) declares what it needs through its constructor. The DI container (the logistics team) reads those requirements and delivers the right objects. Your class never calls new EmailService() itself — the container handles that. This means:

1. You can swap implementations without touching the class that uses them.
2. In tests, you can provide a fake/mock implementation instead of the real one.
3. The lifetime of each object (how long it lives) is managed centrally.

This is the essence of loose coupling — components depend on abstractions (interfaces), not concrete implementations.

The Problem Without DI

Consider a controller that sends a welcome email when a user registers. Without DI, you might write it like this: 

// Tightly coupled — hard to test, hard to change
public class UserController
{
    private readonly EmailService _emailService;

    public UserController()
    {
        // The controller creates its own dependency
        _emailService = new EmailService("smtp.myserver.com", 587);
    }

    public void Register(User user)
    {
        // ... register logic ...
        _emailService.Send(user.Email, "Welcome!", "Thanks for signing up.");
    }
}

Problems: to test Register(), you must have a working SMTP server running. If you want to use a different email provider, you must change UserController. If EmailService needs new constructor parameters, every class that creates one must be updated. This is tight coupling.

Constructor Injection — The Solution

With DI, the controller asks for what it needs — it doesn't create it: 

// Loosely coupled — depends on an interface, not a concrete class
public class UserController : ControllerBase
{
    private readonly IEmailService _emailService;

    // The DI container will provide the IEmailService implementation
    public UserController(IEmailService emailService)
    {
        _emailService = emailService;
    }

    [HttpPost]
    public IActionResult Register([FromBody] RegisterRequest request)
    {
        // ... register logic ...
        _emailService.Send(request.Email, "Welcome!", "Thanks for signing up.");
        return Ok();
    }
}

Now UserController depends on the interface IEmailService, not the concrete EmailService. In tests, you can pass a FakeEmailService that just records what it was asked to send, without touching any SMTP server.

Defining the Interface and Implementation

// The contract — what any email service must be able to do
public interface IEmailService
{
    void Send(string to, string subject, string body);
}

// The real implementation
public class SmtpEmailService : IEmailService
{
    private readonly string _smtpHost;

    public SmtpEmailService(string smtpHost)
    {
        _smtpHost = smtpHost;
    }

    public void Send(string to, string subject, string body)
    {
        // Real SMTP sending logic here
        Console.WriteLine($"Sending to {to} via {_smtpHost}: {subject}");
    }
}

// A fake for testing
public class FakeEmailService : IEmailService
{
    public List<string> SentEmails = new();

    public void Send(string to, string subject, string body)
    {
        SentEmails.Add($"{to}: {subject}");
    }
}

Registering Services in Program.cs

Before the DI container can inject a service, you must register it. You do this in the build phase of Program.cs: 

var builder = WebApplication.CreateBuilder(args);

// Register IEmailService → SmtpEmailService
// When anything asks for IEmailService, provide a SmtpEmailService
builder.Services.AddScoped<IEmailService, SmtpEmailService>();

// Register controllers (UserController, etc.)
builder.Services.AddControllers();

var app = builder.Build();
app.MapControllers();
app.Run();

Now when ASP.NET Core creates a UserController to handle a request, it sees the constructor requires an IEmailService, looks up its registry, finds SmtpEmailService is registered, creates one, and passes it in. Your controller never knows or cares about the concrete type.

The Three Service Lifetimes

One of the most important decisions when registering a service is choosing its lifetime — how long the DI container keeps an instance alive.

📚 Transient — A New Napkin Every Time

AddTransient<T>() — A brand new instance is created every single time the service is requested from the container.

Real-world analogy: like a paper napkin at a restaurant — you use it once and it's gone. Nobody shares napkins. This is for lightweight, stateless services where sharing state between callers would be a problem.

Use for: operations that are cheap to create and have no shared state.

📚 Scoped — One Per Table (Per Request)

AddScoped<T>() — One instance is created per HTTP request. All services within that request get the same instance, but a different one is created for the next request.

Real-world analogy: like a table at a restaurant. All the diners at your table share the same waiter for the evening, but the next table has their own waiter.

Use for: database contexts (Entity Framework's DbContext), unit-of-work objects, anything that should be consistent within a single request but not shared across requests. This is the most common lifetime for services in ASP.NET Core.

📚 Singleton — One Instance for the Whole Restaurant

AddSingleton<T>() — One instance is created the first time it is requested and that same instance is reused for the lifetime of the application.

Real-world analogy: like the restaurant manager. There is one manager. Every waiter, every kitchen station, everyone talks to the same manager.

Use for: expensive-to-create objects, in-memory caches, configuration holders, or services that maintain application-wide state. Be careful: singleton services must be thread-safe because multiple requests may use them simultaneously. 

// Registering services with different lifetimes
builder.Services.AddTransient<IGuidGenerator, RandomGuidGenerator>();
builder.Services.AddScoped<IProductRepository, ProductRepository>();
builder.Services.AddScoped<IEmailService, SmtpEmailService>();
builder.Services.AddSingleton<IAppCache, InMemoryCache>();

// You can also register a concrete type without an interface
builder.Services.AddScoped<OrderProcessor>();

// Or register a specific instance you created yourself
var settings = new AppSettings { MaxPageSize = 100 };
builder.Services.AddSingleton(settings);
💡 The Captive Dependency Trap

Never inject a Scoped or Transient service into a Singleton. The singleton lives forever, and by capturing a scoped service in its constructor, it prevents that scoped service from being properly released after the request ends. ASP.NET Core will even throw an exception in development mode to warn you. The rule: a service's dependencies must have a lifetime equal to or longer than the service itself.

🔎 DI is Everywhere in ASP.NET Core

The built-in ASP.NET Core services you used in Chapter 14 — AddControllers(), AddEndpointsApiExplorer(), AddSwaggerGen() — are all just calls to register services into the same DI container you are using for your own code. Logging, configuration, the HTTP context — it is all delivered via DI. Once you understand the pattern, the entire framework becomes readable.

📚 Key Terms

Dependency Injection (DI): A design pattern where a class receives its dependencies from an external source rather than creating them itself.

DI Container: The system that manages creating, storing, and delivering service instances. In ASP.NET Core, this is accessed via builder.Services.

Constructor Injection: The preferred DI pattern — dependencies are declared as parameters in the class constructor.

Transient: A new instance is created every time the service is requested.

Scoped: One instance per HTTP request. Different requests get different instances.

Singleton: One instance for the entire application lifetime.

Loose Coupling: A design goal where components depend on abstractions (interfaces) rather than concrete implementations, making them easier to swap and test.

Chapter Summary

  • Dependency Injection inverts the responsibility of creating objects — classes declare what they need, and the DI container provides it.
  • ASP.NET Core has DI built in. All services are registered via builder.Services in Program.cs.
  • Constructor injection is the standard pattern: declare your dependency as a constructor parameter and the container fills it in automatically.
  • Depending on interfaces, not concrete classes, gives you loose coupling — easy to swap implementations and easy to test.
  • The three lifetimes are: Transient (new per request), Scoped (one per HTTP request), and Singleton (one for the app's lifetime).
  • Scoped is the most common lifetime for services in web applications — especially for database contexts.
  • Never inject a Scoped or Transient service into a Singleton — this creates a "captive dependency" that can cause subtle bugs.
