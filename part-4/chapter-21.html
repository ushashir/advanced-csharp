JWT Authentication — The Digital Wristband

JSON Web Tokens are the currency of modern API authentication. They are compact, self-contained, and stateless — everything the server needs to know about you is encoded right inside the token. No database lookup required on every request.

What you'll learn in this chapter

  • What a JWT is and the three parts separated by dots (header.payload.signature)
  • What claims are and which standard ones matter (sub, email, role, exp)
  • Why JWTs are stateless — and why that is both a strength and a limitation
  • How to add and configure the Microsoft.AspNetCore.Authentication.JwtBearer package
  • How to generate a JWT on login using JwtSecurityTokenHandler
  • How to protect endpoints and read claims from HttpContext.User
  • A complete login + protected profile endpoint example

The Festival Wristband

Imagine you arrive at a three-day music festival. At the entrance gate, a staff member checks your ticket, confirms your identity, and snaps a wristband onto your wrist. The wristband is colour-coded: green for general admission, gold for VIP backstage access. From that moment on, you never need to show your original ticket again. At every gate, every bar, every stage entrance — the staff simply look at your wristband.

That wristband is a JWT. It is issued once at login, carries information about who you are and what you are allowed to do, and you present it on every subsequent request. The server does not need to look you up in a database — everything it needs is encoded in the token itself.

🎪 The Festival Wristband Analogy

Login = Getting your wristband at the gate. You present your ticket (credentials), the gate staff verify you (authentication), and you receive your wristband (JWT).

Subsequent API calls = Showing your wristband at each venue. No one checks your original ticket again — they just verify the wristband is genuine (validate the signature) and read what it says (claims).

Expiry = The wristband stops working after three days. JWTs have an expiration time (exp claim). When they expire, the user must log in again to get a fresh token.

The secret key = The special holographic material in the wristband that can't be faked. Only the festival (your server) knows the secret used to create it, so counterfeits are immediately detected.

Anatomy of a JWT — Three Parts, One String

A JWT is a string of three Base64URL-encoded parts separated by dots:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9 . eyJzdWIiOiJ1c2VyLTEyMyIsImVtYWlsIjoiYWxpY2VAZXhhbXBsZS5jb20iLCJyb2xlIjoiQWRtaW4iLCJleHAiOjE3MDAwMDAwMDB9 . SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c FORMAT: Header.Payload.Signature

Part 1: Header

Contains metadata about the token — specifically the algorithm used to sign it: 

{
  "alg": "HS256",   // Algorithm: HMAC SHA-256
  "typ": "JWT"     // Token type
}

Part 2: Payload (Claims)

The payload contains the claims — statements about the user and the token itself. There are standard registered claims and custom claims: 

{
  "sub": "user-123",              // Subject: the user's unique ID
  "email": "alice@example.com",   // Custom claim: user's email
  "role": "Admin",               // Custom claim: user's role
  "iat": 1700000000,             // Issued At: Unix timestamp
  "exp": 1700003600              // Expiration: Unix timestamp (1 hour later)
}
⚠️ The Payload is NOT Encrypted

The JWT payload is Base64URL-encoded, not encrypted. Anyone who obtains the token can decode and read the claims. Never put sensitive information (passwords, credit card numbers, private keys) in a JWT payload. For sensitive payloads, use JWE (JSON Web Encryption) instead. The signature guarantees integrity (no one has tampered with the token) — but not confidentiality.

Part 3: Signature

The signature is computed by the server using the header, payload, and a secret key: 

HMACSHA256(
    base64UrlEncode(header) + "." + base64UrlEncode(payload),
    secretKey
)

When the server receives a JWT, it recomputes the signature using the same secret key. If the result matches the signature in the token, the token is genuine and untampered. If anyone modifies the payload (changing a role from "User" to "Admin", for example), the signature will not match and the token is rejected.

Setting Up JWT in ASP.NET Core

First, install the JWT Bearer package: 

dotnet add package Microsoft.AspNetCore.Authentication.JwtBearer

Add your JWT settings to appsettings.json:

{
  "Jwt": {
    "Key": "your-super-secret-key-must-be-at-least-256-bits-long!",
    "Issuer": "https://yourdomain.com",
    "Audience": "https://yourdomain.com",
    "ExpiryMinutes": 60
  }
}

Configure authentication in Program.cs:

using Microsoft.AspNetCore.Authentication.JwtBearer;
using Microsoft.IdentityModel.Tokens;
using System.Text;

var builder = WebApplication.CreateBuilder(args);

var jwtKey = builder.Configuration["Jwt:Key"]!;
var jwtIssuer = builder.Configuration["Jwt:Issuer"]!;
var jwtAudience = builder.Configuration["Jwt:Audience"]!;

builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true,
            ValidateAudience = true,
            ValidateLifetime = true,          // Reject expired tokens
            ValidateIssuerSigningKey = true,   // Verify the signature
            ValidIssuer = jwtIssuer,
            ValidAudience = jwtAudience,
            IssuerSigningKey = new SymmetricSecurityKey(
                Encoding.UTF8.GetBytes(jwtKey))
        };
    });

builder.Services.AddAuthorization();
builder.Services.AddControllers();

var app = builder.Build();

app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();

app.Run();
📚 Key Term: SymmetricSecurityKey

A signing key where the same secret is used both to sign (create) and to verify (validate) the JWT. This is the HMAC approach. The alternative is asymmetric signing (RS256), where a private key signs the token and a public key verifies it — useful when multiple services need to validate tokens without knowing the private secret.

Generating a JWT on Login

Here is a complete AuthController that accepts credentials and returns a JWT: 

using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Mvc;
using Microsoft.IdentityModel.Tokens;
using System.IdentityModel.Tokens.Jwt;
using System.Security.Claims;
using System.Text;

public record LoginRequest(string Email, string Password);
public record LoginResponse(string Token, DateTime ExpiresAt);

[ApiController]
[Route("auth")]
public class AuthController : ControllerBase
{
    private readonly IConfiguration _config;

    public AuthController(IConfiguration config) => _config = config;

    [AllowAnonymous]
    [HttpPost("login")]
    public IActionResult Login([FromBody] LoginRequest request)
    {
        // In a real app: validate credentials against the database
        if (request.Email != "alice@example.com" || request.Password != "password123")
            return Unauthorized(new { Message = "Invalid credentials" });

        var token = GenerateJwt(userId: "user-123", email: request.Email, role: "Admin");
        return Ok(token);
    }

    private LoginResponse GenerateJwt(string userId, string email, string role)
    {
        var key = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(_config["Jwt:Key"]!));
        var credentials = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);

        var claims = new[]
        {
            new Claim(JwtRegisteredClaimNames.Sub, userId),
            new Claim(JwtRegisteredClaimNames.Email, email),
            new Claim(ClaimTypes.Role, role),
            new Claim(JwtRegisteredClaimNames.Jti, Guid.NewGuid().ToString())
        };

        var expiresAt = DateTime.UtcNow.AddMinutes(
            int.Parse(_config["Jwt:ExpiryMinutes"] ?? "60"));

        var tokenDescriptor = new JwtSecurityToken(
            issuer: _config["Jwt:Issuer"],
            audience: _config["Jwt:Audience"],
            claims: claims,
            expires: expiresAt,
            signingCredentials: credentials
        );

        var tokenString = new JwtSecurityTokenHandler().WriteToken(tokenDescriptor);

        return new LoginResponse(tokenString, expiresAt);
    }
}

A Protected Profile Endpoint

Now let's create an endpoint that requires authentication and reads claims from the token: 

[Authorize]
[ApiController]
[Route("profile")]
public class ProfileController : ControllerBase
{
    [HttpGet]
    public IActionResult GetProfile()
    {
        // Read claims from the validated JWT — ASP.NET Core populates these
        var userId  = User.FindFirst(JwtRegisteredClaimNames.Sub)?.Value;
        var email   = User.FindFirst(JwtRegisteredClaimNames.Email)?.Value;
        var role    = User.FindFirst(ClaimTypes.Role)?.Value;

        return Ok(new
        {
            UserId  = userId,
            Email   = email,
            Role    = role,
            Message = "Your JWT was valid — welcome!"
        });
    }

    // Only Admins can access this endpoint
    [Authorize(Roles = "Admin")]
    [HttpGet("admin-dashboard")]
    public IActionResult GetAdminDashboard()
    {
        return Ok("Welcome to the admin dashboard!");
    }
}

To call the protected endpoint, the client sends the token in the Authorization header: 

GET /profile HTTP/1.1
Host: localhost:5000
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...

Why JWTs are Stateless

Traditional session-based authentication stores session data on the server — typically in memory or a database. Every request requires a database lookup: "Is session ID 'abc123' still valid? Who does it belong to?"

JWTs are different. All the information the server needs — user ID, role, expiry — is inside the token itself. The server just validates the signature (a fast cryptographic operation) and reads the claims. No database hit required.

⚖️ Stateless vs Stateful — The Trade-offs

Stateless JWT advantages: No server-side session storage, scales easily across multiple servers (any server can validate the token), works great for APIs and microservices.

Stateless JWT limitations: You cannot instantly revoke a JWT before it expires (unlike a session, which you can delete from the server). Common solutions: short expiry times (15–60 minutes) combined with a refresh token flow, or a token blacklist in Redis for revocation when needed.

The Secret Key — Protect It With Your Life

The JWT secret key is the most important security asset in a JWT-based system. Anyone who obtains the secret key can create valid tokens for any user with any role. Treat it like a private key or a database password.

  • Never commit the secret key to version control — use environment variables or a secrets manager.
  • Use at least 256 bits of entropy (32+ random characters for HMAC-SHA256).
  • Rotate the key periodically (this will invalidate all existing tokens — plan accordingly).
  • In production, use Azure Key Vault, AWS Secrets Manager, or HashiCorp Vault.
// Development: use dotnet user-secrets
dotnet user-secrets set "Jwt:Key" "your-32-character-secret-key-here!!"

// Production: use environment variables
// export Jwt__Key="your-32-character-secret-key-here!!"
// Note: double underscore __ separates nested config sections
📚 Key Terms Summary

JWT (JSON Web Token): A compact, self-contained token format consisting of three Base64URL-encoded parts: header, payload (claims), and signature.

Claims: Key-value pairs inside a JWT payload that assert facts about the user (sub, email, role, exp).

JwtSecurityTokenHandler: The .NET class used to create and validate JWTs.

SigningCredentials: Wraps the signing key and algorithm used to create the JWT signature.

Bearer token: An authentication scheme where the client presents a token in the Authorization: Bearer <token> header.

Stateless authentication: Authentication that requires no server-side session storage — the token itself carries all necessary information.

Chapter Summary

  • A JWT has three parts separated by dots: header (algorithm), payload (claims), and signature.
  • The payload contains claims like sub (user ID), email, role, and exp (expiry) — it is encoded, not encrypted.
  • JWTs are stateless — all information is in the token, no server-side session lookup needed.
  • Add JWT support with Microsoft.AspNetCore.Authentication.JwtBearer and configure TokenValidationParameters.
  • Generate tokens using JwtSecurityToken, SigningCredentials, and JwtSecurityTokenHandler.WriteToken().
  • Read claims in controllers via HttpContext.User.FindFirst("claimType")?.Value.
  • The secret key must be protected — use environment variables or a secrets manager, never plain appsettings.json in production.
