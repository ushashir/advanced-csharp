Authentication & Authorization — The Bouncer and the Guest List

Every serious web application needs to know two things about its users: who are you, and what are you allowed to do? These are two separate questions, and ASP.NET Core answers them with a two-layer security system that is both powerful and elegantly designed.

What you'll learn in this chapter

  • The exact difference between authentication and authorization
  • An overview of ASP.NET Core Identity
  • How to use the [Authorize] attribute to protect endpoints
  • Roles vs Claims — two different ways to model permissions
  • Policy-based authorization with AddAuthorization
  • Why middleware order matters (UseAuthentication before UseAuthorization)
  • Cookie authentication vs token authentication — a preview

The Bouncer and the Guest List

Picture a high-end nightclub. At the door stands a bouncer. When you arrive, the first thing the bouncer does is check your ID — your driving licence, your passport, something that proves who you are. That is authentication: the process of verifying your identity.

Once the bouncer is satisfied that you are who you say you are, they check the guest list. Are you on the regular list? You get in and can use the bar and the dance floor. Are you on the VIP list? You get access to the private lounge upstairs. Not on any list? You stay outside. That is authorization: determining what you are allowed to do after your identity has been confirmed.

🚪 The Nightclub Analogy

Authentication = "Are you who you say you are?"
The bouncer checks your ID. You prove your identity. This happens once, at the door. In a web app, this is typically the login process — you prove you are "alice@example.com" by providing a password (or a token, or a social login).

Authorization = "Are you allowed to do this?"
The guest list determines which areas you can access inside the club. In a web app, this is every subsequent check: can this user view the admin dashboard? Can they delete other users' posts? Are they allowed to access the billing API?

You cannot be authorized without first being authenticated. But being authenticated does not automatically mean you are authorized for everything.

ASP.NET Core Identity — The Security Framework

ASP.NET Core ships with a built-in membership system called ASP.NET Core Identity. It handles the most common security concerns out of the box:

  • User registration and login
  • Secure password hashing (PBKDF2 by default — never stored in plain text)
  • Email confirmation and password reset
  • Role management (Admin, User, Manager, etc.)
  • Two-factor authentication (2FA)
  • Account lockout after too many failed login attempts
  • Integration with external providers (Google, Facebook, GitHub via OAuth)

Identity stores user data in a database — typically via Entity Framework Core. The core tables it creates include AspNetUsers, AspNetRoles, AspNetUserRoles, and AspNetUserClaims.

You add Identity to your project with:

// In your terminal
dotnet add package Microsoft.AspNetCore.Identity.EntityFrameworkCore

And configure it in Program.cs:

var builder = WebApplication.CreateBuilder(args);

// Register Identity services
builder.Services
    .AddIdentity<IdentityUser, IdentityRole>()
    .AddEntityFrameworkStores<AppDbContext>()
    .AddDefaultTokenProviders();

var app = builder.Build();

// IMPORTANT: order matters here
app.UseAuthentication();   // Who are you?
app.UseAuthorization();    // What can you do?

app.Run();
📚 Key Term: ASP.NET Core Identity

A built-in membership system for ASP.NET Core applications. It provides user management, password hashing, role management, and external login provider support. It integrates with Entity Framework Core to persist user data and can be extended to accommodate custom user properties.

The [Authorize] Attribute — The VIP Stamp

The [Authorize] attribute is the most fundamental tool in ASP.NET Core security. Apply it to a controller or an individual action method, and ASP.NET Core will reject any unauthenticated request with a 401 Unauthorized response before your code even runs. 

using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Mvc;

// Applied to the whole controller — every action is protected
[Authorize]
[ApiController]
[Route("api/[controller]")]
public class ProfileController : ControllerBase
{
    [HttpGet]
    public IActionResult GetProfile()
    {
        var userId = User.FindFirst("sub")?.Value;
        return Ok(new { UserId = userId, Message = "You are authenticated!" });
    }

    // This specific action allows anonymous access even though the controller is [Authorize]
    [AllowAnonymous]
    [HttpGet("public")]
    public IActionResult PublicInfo()
    {
        return Ok("This is visible to everyone.");
    }
}

The complementary attribute is [AllowAnonymous], which explicitly opens an endpoint to unauthenticated users — even when the parent controller is locked with [Authorize].

💡 Secure by Default

A common pattern is to apply [Authorize] globally (so every endpoint is protected by default) and then add [AllowAnonymous] only to the specific endpoints that should be public, like the login endpoint or a health check. This "secure by default" approach means you can never accidentally forget to protect an endpoint. 

// Apply [Authorize] globally in Program.cs
builder.Services.AddControllers(options =>
{
    var policy = new AuthorizationPolicyBuilder()
        .RequireAuthenticatedUser()
        .Build();
    options.Filters.Add(new AuthorizeFilter(policy));
});

Roles vs Claims — Two Ways to Think About Permissions

ASP.NET Core gives you two complementary models for authorization: roles and claims. Understanding the difference is important.

Roles

A role is a named group that a user belongs to. Common examples: Admin, Manager, User, Editor. You restrict access to a role using: 

// Only users in the "Admin" role can access this
[Authorize(Roles = "Admin")]
[HttpDelete("{id}")]
public IActionResult DeleteUser(int id) { ... }

// Accessible to Admin OR Manager
[Authorize(Roles = "Admin,Manager")]
[HttpGet("reports")]
public IActionResult GetReports() { ... }

Claims

A claim is a key-value piece of information about a user — more fine-grained than a role. Examples: email = "alice@example.com", department = "engineering", subscription_tier = "premium". Claims are issued by an identity provider and travel with the user's token. 

// Check a claim in code
var department = User.FindFirst("department")?.Value;
if (department != "engineering")
    return Forbid();
🏷️ Roles vs Claims Analogy

Think of a company badge. Your role is your job title printed on the badge: "Engineer", "Manager", "Security". It gives broad access. Your claims are all the other details: your employee ID, which floor you have access to, whether you can enter the server room, what department you are in. Claims are more precise and flexible than roles.

Policy-Based Authorization — The Rule Book

When role-based authorization isn't expressive enough, ASP.NET Core has a more powerful system: policies. A policy is a named set of requirements. You define policies once in Program.cs and reference them by name in your attributes. 

// Program.cs — define policies
builder.Services.AddAuthorization(options =>
{
    // Simple role policy
    options.AddPolicy("AdminOnly", policy =>
        policy.RequireRole("Admin"));

    // Claim-based policy
    options.AddPolicy("PremiumUser", policy =>
        policy.RequireClaim("subscription_tier", "premium"));

    // Combined requirements: authenticated + specific claim
    options.AddPolicy("EngineeringStaff", policy =>
        policy
            .RequireAuthenticatedUser()
            .RequireClaim("department", "engineering"));

    // Custom requirement using a lambda (minimum age example)
    options.AddPolicy("Over18", policy =>
        policy.RequireAssertion(context =>
        {
            var ageClaim = context.User.FindFirst("age");
            return ageClaim != null && int.Parse(ageClaim.Value) >= 18;
        }));
});

Then use the policy name in your attribute:

[Authorize(Policy = "PremiumUser")]
[HttpGet("premium-content")]
public IActionResult GetPremiumContent()
{
    return Ok("Here is your exclusive premium content!");
}

[Authorize(Policy = "EngineeringStaff")]
[HttpGet("deploys")]
public IActionResult GetDeployments()
{
    return Ok("Deployment pipeline access granted.");
}
📚 Key Term: Authorization Policy

A named set of requirements that a user must satisfy to access a resource. Policies are defined once in AddAuthorization() and referenced by name in [Authorize(Policy = "...")]. They are more flexible and reusable than inline role checks.

Why Middleware Order Matters

This is one of the most common mistakes ASP.NET Core beginners make. The middleware pipeline in ASP.NET Core is ordered — each piece of middleware runs in the sequence you register it, and UseAuthentication must come before UseAuthorization. 

// CORRECT order in Program.cs
app.UseRouting();

app.UseAuthentication();   // Step 1: identify the user (set HttpContext.User)
app.UseAuthorization();    // Step 2: check if the user can do this (requires Step 1)

app.MapControllers();
// WRONG — Authorization runs before Authentication has identified the user
app.UseAuthorization();    // ❌ HttpContext.User is still anonymous
app.UseAuthentication();   // Too late! The check already happened

Think of it like a bouncer and a list-checker. The bouncer (authentication) must verify your ID and stamp your hand before the list-checker (authorization) looks at what your stamp says. If the list-checker goes first, they see a blank hand and deny everyone.

⚠️ Common Mistake: Wrong Middleware Order

If your [Authorize] attributes seem to be doing nothing — or if every request is being rejected regardless of credentials — middleware order is the first thing to check. It has caught many developers off guard, from beginners to experienced engineers switching from other frameworks.

Cookie Authentication vs Token Authentication

ASP.NET Core supports multiple authentication schemes. The two most common are:

Cookie Authentication

Used primarily for browser-based web applications. When a user logs in, the server creates a session and sets an encrypted cookie in the browser. On subsequent requests, the browser automatically sends the cookie and the server validates it. Works beautifully for traditional web apps with server-rendered pages. 

// Adding cookie authentication
builder.Services
    .AddAuthentication(CookieAuthenticationDefaults.AuthenticationScheme)
    .AddCookie(options =>
    {
        options.LoginPath = "/account/login";
        options.LogoutPath = "/account/logout";
        options.ExpireTimeSpan = TimeSpan.FromHours(8);
    });

Token Authentication (JWT)

Used for APIs, mobile apps, and single-page applications (SPAs). When a user logs in, the server issues a JSON Web Token (JWT). The client stores this token and sends it with every request in the Authorization: Bearer <token> header. The server validates the token on each request — with no server-side session storage needed. We cover this in depth in the next chapter.

💡 Which to Choose?

Cookie auth is great for traditional web apps where the browser handles everything automatically. JWT / token auth is better for APIs consumed by mobile apps, SPAs (React, Angular, Vue), or other services. Most modern full-stack applications use JWT for their API layer.

Putting It All Together — A Minimal Secure API

var builder = WebApplication.CreateBuilder(args);

// 1. Add authentication and authorization services
builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(); // configuration covered in Chapter 21

builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("AdminOnly", p => p.RequireRole("Admin"));
});

builder.Services.AddControllers();

var app = builder.Build();

// 2. Register middleware IN THE CORRECT ORDER
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();

app.Run();
📚 Key Terms Summary

Authentication (AuthN): The process of verifying who a user is. "Are you who you claim to be?"

Authorization (AuthZ): The process of determining what a user is allowed to do. "Are you permitted to do this?"

[Authorize]: An ASP.NET Core attribute that restricts access to authenticated (and optionally, specifically permitted) users.

[AllowAnonymous]: Overrides [Authorize] to allow unauthenticated access to a specific endpoint.

Claim: A key-value pair representing a fact about a user (name, email, role, department, etc.) that travels with their identity token.

Policy: A named set of authorization requirements, defined once and reused across the application.

Chapter Summary

  • Authentication (AuthN) verifies identity; Authorization (AuthZ) grants or denies access — they are separate concerns that work in sequence.
  • ASP.NET Core Identity provides a complete membership system: users, passwords, roles, 2FA, and external providers.
  • The [Authorize] attribute restricts endpoints to authenticated users; [AllowAnonymous] creates exceptions.
  • Roles group users into broad categories (Admin, User); Claims carry fine-grained key-value facts about a user.
  • Policy-based authorization with AddAuthorization(options => options.AddPolicy(...)) is the most flexible approach.
  • UseAuthentication() must always come before UseAuthorization() in the middleware pipeline — order is critical.
  • Cookie auth suits browser applications; JWT / Bearer token auth suits APIs and SPAs.
