Part 3 · Chapter 19

Configuration — Your App's Settings Book

A well-built application never has credentials, URLs, or feature flags baked into its code. Everything that might change between environments — or needs to be secret — belongs in configuration. ASP.NET Core has a rich, flexible configuration system that makes this easy and safe.

What you'll learn in this chapter

  • appsettings.json — the primary configuration file
  • Environment-specific settings: appsettings.Development.json
  • Reading configuration values in code
  • The Options pattern: IOptions<T> for strongly-typed configuration
  • Environment variables as configuration
  • User Secrets for development — never commit passwords
  • Connection strings and email settings as a real example

The Hotel Guest Preferences Analogy

Picture a luxury hotel. Before you arrive, you fill out a preferences card: "I prefer a firm pillow, I'd like the room at 20°C, I take a newspaper with breakfast, and please do not disturb before 8am." When you check in, the hotel reads your card and sets up your room accordingly — without you having to explain your preferences every day.

If you are a VIP guest (think: production environment), the hotel follows strict, locked-down preferences. If you are a journalist on a test visit (development environment), relaxed rules apply — you might get a different setup. The card is your appsettings.json; the special overrides for different visit types are your appsettings.Development.json and environment variables.

🏨 The Settings Book

Your app reads its "preferences card" at startup. The base card (appsettings.json) has defaults. The environment-specific overlay (appsettings.Development.json) overrides those defaults for the current environment. Environment variables override everything — they are the hotel manager's direct instructions that trump any written preferences.

This layered override system means developers never need to touch production settings, and production settings never bleed into development.

appsettings.json

Every ASP.NET Core project is created with an appsettings.json in the project root. It is a JSON file with a hierarchical structure: 

// appsettings.json
{
  "ConnectionStrings": {
    "DefaultConnection": "Server=localhost;Database=MyAppDb;Trusted_Connection=true;"
  },
  "EmailSettings": {
    "SmtpHost":     "smtp.mycompany.com",
    "SmtpPort":     587,
    "FromAddress":  "noreply@mycompany.com",
    "FromName":     "MyApp Notifications"
  },
  "Logging": {
    "LogLevel": {
      "Default":             "Information",
      "Microsoft.AspNetCore": "Warning"
    }
  },
  "AllowedHosts": "*"
}

Environment-Specific Overrides

ASP.NET Core automatically loads appsettings.{EnvironmentName}.json on top of the base file. The environment is set by the ASPNETCORE_ENVIRONMENT environment variable. In development, it defaults to Development. 

// appsettings.Development.json — overrides for local development only
{
  "ConnectionStrings": {
    "DefaultConnection": "Data Source=dev.db"
  },
  "EmailSettings": {
    "SmtpHost": "localhost",
    "SmtpPort": 1025
  },
  "Logging": {
    "LogLevel": {
      "Default": "Debug"
    }
  }
}

In production, ASPNETCORE_ENVIRONMENT is set to Production, and appsettings.Production.json would override the base — or better yet, secrets are injected as environment variables so they are never stored in files.

💡 The Configuration Priority Order

ASP.NET Core loads configuration from multiple sources in this priority order (later sources override earlier ones):

  1. appsettings.json — lowest priority, safe defaults
  2. appsettings.{Environment}.json — environment-specific overrides
  3. User Secrets (development only)
  4. Environment variables — high priority
  5. Command-line arguments — highest priority

This means you can always override any setting without changing files — just set an environment variable on the server.

Reading Configuration Directly

You can inject IConfiguration anywhere and read values with bracket notation or GetSection. This is the simplest approach but the least type-safe: 

// Inject IConfiguration into a class via constructor
public class SomeService
{
    private readonly IConfiguration _config;

    public SomeService(IConfiguration config)
    {
        _config = config;
    }

    public void DoSomething()
    {
        // Read a single value using colon-separated path
        string host = _config["EmailSettings:SmtpHost"] ?? "localhost";
        int    port = _config.GetValue<int>("EmailSettings:SmtpPort");

        // Read the entire EmailSettings section as a dictionary
        var emailSection = _config.GetSection("EmailSettings");
        string? from = emailSection["FromAddress"];
    }
}

The Options Pattern — Strongly-Typed Configuration

The options pattern is the recommended approach for reading groups of related configuration values. You define a plain C# class that mirrors your config section, then bind it. This gives you type safety, IntelliSense, and validation. 

// 1. Define a strongly-typed options class
public class EmailSettings
{
    // Constant matches the JSON section name (used in AddOptions call)
    public const string SectionName = "EmailSettings";

    public string SmtpHost    { get; set; } = string.Empty;
    public int    SmtpPort    { get; set; }
    public string FromAddress { get; set; } = string.Empty;
    public string FromName    { get; set; } = string.Empty;
}

// 2. Register in Program.cs
builder.Services
    .AddOptions<EmailSettings>()
    .BindConfiguration(EmailSettings.SectionName)
    .ValidateDataAnnotations()
    .ValidateOnStart();

// Shorter alternative:
builder.Services.Configure<EmailSettings>(
    builder.Configuration.GetSection(EmailSettings.SectionName));

// 3. Inject and use with IOptions<T>
public class SmtpEmailService : IEmailService
{
    private readonly EmailSettings _settings;

    public SmtpEmailService(IOptions<EmailSettings> options)
    {
        _settings = options.Value;
    }

    public void Send(string to, string subject, string body)
    {
        Console.WriteLine(
            $"Sending via {_settings.SmtpHost}:{_settings.SmtpPort} from {_settings.FromAddress}");
        // Real SMTP logic here...
    }
}

User Secrets — Dev-Only Secure Values

Never put real passwords, API keys, or connection strings with credentials in appsettings.json. That file is typically committed to source control. Instead, use User Secrets for development: 

# Enable user secrets in your project (run once)
dotnet user-secrets init

# Store a secret — saved in your OS user profile, NOT in the project folder
dotnet user-secrets set "EmailSettings:SmtpPassword" "my-real-password"
dotnet user-secrets set "ConnectionStrings:DefaultConnection" "Server=prod;Password=secret"

# List all secrets
dotnet user-secrets list

User secrets are stored in ~/.microsoft/usersecrets/{project-id}/secrets.json on your machine — outside the project directory, so they are never accidentally committed. They are automatically loaded in Development mode.

Environment Variables — Production Secrets

In production (on a server or cloud container), use environment variables. ASP.NET Core automatically reads them as configuration. Nested values use double underscores as separators: 

# Setting an environment variable on Linux/macOS
export EmailSettings__SmtpPassword="production-password"
export ConnectionStrings__DefaultConnection="Server=prod-db;..."

# On Windows (PowerShell)
$env:EmailSettings__SmtpPassword = "production-password"

In cloud platforms like Azure App Service, AWS ECS, or Kubernetes, you set these in the platform's "environment variables" or "secrets" configuration UI, and ASP.NET Core reads them automatically at startup.

🔐 The Golden Rule of Secrets

Never hardcode secrets. Never commit secrets to source control. Not even for "just testing." Leaked credentials in git history can be found years later. The proper approach:

Development → User Secrets (local, never committed)
CI/CD pipelines → Secret variables in GitHub Actions / Azure DevOps
Production servers → Environment variables or a secrets manager (Azure Key Vault, AWS Secrets Manager, HashiCorp Vault)

📚 Key Terms

appsettings.json: The primary configuration file for ASP.NET Core applications. Safe for non-secret settings.

appsettings.Development.json: Environment-specific configuration override loaded only in the Development environment.

IOptions<T>: An interface for injecting strongly-typed configuration. IOptions<T>.Value gives you the bound configuration object.

User Secrets: A development-only mechanism for storing sensitive values outside the project directory so they are never committed to source control.

Options Pattern: The recommended approach in ASP.NET Core for reading groups of related configuration values as a strongly-typed C# class.

ASPNETCORE_ENVIRONMENT: An environment variable that controls which environment-specific configuration file is loaded. Common values: Development, Staging, Production.

Chapter Summary

  • appsettings.json is the primary configuration file. Use it for non-secret settings with safe defaults.
  • appsettings.Development.json automatically overrides the base file in the Development environment — perfect for using a local database during development.
  • Configuration sources are layered: appsettings → environment-specific → User Secrets → environment variables → command line. Later sources win.
  • The Options pattern (IOptions<T>) provides strongly-typed, DI-friendly access to configuration sections — strongly preferred over raw IConfiguration access.
  • User Secrets are the right tool for development-time secrets. They are stored outside the project and never committed.
  • In production, use environment variables or a secrets manager. Never put passwords in files committed to source control.
