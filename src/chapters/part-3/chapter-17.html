Part 3 · Chapter 17

Controllers, Services, and Repositories

A controller that does everything — validates input, applies business rules, and queries the database — is a nightmare to maintain and impossible to test. In this chapter, we separate those responsibilities into three clean layers, each with a single job.

What you'll learn in this chapter

  • Why layered architecture matters — separation of concerns
  • The Controller layer: handling HTTP, nothing more
  • The Service layer: home of your business logic
  • The Repository layer: abstracting data access
  • The IRepository pattern and why interfaces matter here
  • DTOs (Data Transfer Objects) vs domain models
  • A complete ProductController → IProductService → IProductRepository chain

The Restaurant Kitchen Analogy

A professional restaurant kitchen has clear roles and a strict chain of command. The waiter (front-of-house) takes orders from customers, delivers food, and handles complaints. The waiter does not cook. The chef (kitchen) receives tickets from the waiter, applies culinary expertise, and coordinates the cooking. The chef does not serve tables. The pantry (larder) stores all the raw ingredients and handles restocking. The pantry does not cook or serve.

Each layer communicates only with the layer directly below it. The waiter passes tickets to the chef; the chef fetches ingredients from the pantry. No one skips a layer. This is exactly how a well-structured ASP.NET Core application works:

HTTP Request ↓ ┌─────────────────────────────────────┐ │ Controller Layer │ ← Handles HTTP. Calls service. Returns result. │ ProductsController │ └──────────────┬──────────────────────┘ │ calls IProductService ↓ ┌─────────────────────────────────────┐ │ Service Layer │ ← Business logic. Orchestrates. Validates rules. │ ProductService │ └──────────────┬──────────────────────┘ │ calls IProductRepository ↓ ┌─────────────────────────────────────┐ │ Repository Layer │ ← Data access only. No business logic. │ ProductRepository │ └──────────────┬──────────────────────┘ │ queries ↓ Database / Storage

Layer 1: The Controller

The controller's sole job is to be the HTTP boundary. It should:

  • Receive the HTTP request and parse inputs from route, query string, or body.
  • Call the appropriate service method.
  • Map the result to the appropriate HTTP response (200, 201, 404, etc.).

The controller should contain zero business logic and zero database queries. If you find yourself writing if (price < 0) or dbContext.Products.Where(...) inside a controller, something is wrong. 

[ApiController]
[Route("api/[controller]")]
public class ProductsController : ControllerBase
{
    private readonly IProductService _productService;

    public ProductsController(IProductService productService)
    {
        _productService = productService;
    }

    [HttpGet]
    public async Task<ActionResult<IEnumerable<ProductDto>>> GetAll()
    {
        var products = await _productService.GetAllAsync();
        return Ok(products);
    }

    [HttpGet("{id:int}")]
    public async Task<ActionResult<ProductDto>> GetById(int id)
    {
        var product = await _productService.GetByIdAsync(id);
        if (product is null) return NotFound();
        return Ok(product);
    }

    [HttpPost]
    public async Task<ActionResult<ProductDto>> Create([FromBody] CreateProductRequest req)
    {
        var created = await _productService.CreateAsync(req);
        return CreatedAtAction(nameof(GetById), new { id = created.Id }, created);
    }
}

Layer 2: The Service

The service layer is where your application's brain lives. It contains:

  • Business rules ("a product price cannot be negative")
  • Orchestration ("when creating an order, check stock, charge payment, send confirmation email")
  • Mapping between domain models and DTOs
  • Calls to repositories, external services, and other services
// Interface — the contract the controller depends on
public interface IProductService
{
    Task<IEnumerable<ProductDto>> GetAllAsync();
    Task<ProductDto?> GetByIdAsync(int id);
    Task<ProductDto> CreateAsync(CreateProductRequest request);
}

// Implementation — the actual logic
public class ProductService : IProductService
{
    private readonly IProductRepository _repository;

    public ProductService(IProductRepository repository)
    {
        _repository = repository;
    }

    public async Task<IEnumerable<ProductDto>> GetAllAsync()
    {
        var products = await _repository.GetAllAsync();
        return products.Select(ToDto);
    }

    public async Task<ProductDto?> GetByIdAsync(int id)
    {
        var product = await _repository.GetByIdAsync(id);
        return product is null ? null : ToDto(product);
    }

    public async Task<ProductDto> CreateAsync(CreateProductRequest request)
    {
        // Business rule: price must be positive
        if (request.Price <= 0)
            throw new ArgumentException("Price must be greater than zero.");

        var product = new Product { Name = request.Name, Price = request.Price };
        await _repository.AddAsync(product);
        return ToDto(product);
    }

    // Private mapping helper — domain model → DTO
    private static ProductDto ToDto(Product p) =>
        new() { Id = p.Id, Name = p.Name, Price = p.Price };
}

Layer 3: The Repository

The repository layer wraps all data access. Its job is purely to talk to the database (or any storage) and nothing else — no business rules, no HTTP concerns, no logging of business events. 

// Interface — the contract the service depends on
public interface IProductRepository
{
    Task<IEnumerable<Product>> GetAllAsync();
    Task<Product?> GetByIdAsync(int id);
    Task AddAsync(Product product);
    Task UpdateAsync(Product product);
    Task DeleteAsync(int id);
}

// In-memory implementation (before we add EF Core in the next chapter)
public class InMemoryProductRepository : IProductRepository
{
    private readonly List<Product> _store = new();
    private int _nextId = 1;

    public Task<IEnumerable<Product>> GetAllAsync()
        => Task.FromResult(_store.AsEnumerable());

    public Task<Product?> GetByIdAsync(int id)
        => Task.FromResult(_store.FirstOrDefault(p => p.Id == id));

    public Task AddAsync(Product product)
    {
        product.Id = _nextId++;
        _store.Add(product);
        return Task.CompletedTask;
    }

    public Task UpdateAsync(Product product)
    {
        var index = _store.FindIndex(p => p.Id == product.Id);
        if (index >= 0) _store[index] = product;
        return Task.CompletedTask;
    }

    public Task DeleteAsync(int id)
    {
        _store.RemoveAll(p => p.Id == id);
        return Task.CompletedTask;
    }
}

DTOs vs Domain Models

A domain model (entity) is the internal representation of a concept — it maps to a database table and may include navigation properties, computed fields, and internal state.

A DTO (Data Transfer Object) is what you expose to the outside world through your API. It is a flat, simple class shaped for transport. 

// Domain model — internal, mapped to database
public class Product
{
    public int      Id          { get; set; }
    public string   Name        { get; set; } = string.Empty;
    public decimal  Price       { get; set; }
    public bool     IsDeleted   { get; set; }  // soft delete flag — internal only
    public DateTime CreatedAt   { get; set; }
    public DateTime UpdatedAt   { get; set; }
}

// DTO — what the API caller sees (no internal fields exposed)
public class ProductDto
{
    public int     Id    { get; set; }
    public string  Name  { get; set; } = string.Empty;
    public decimal Price { get; set; }
}

// Request DTO — what the caller sends to create a product
public class CreateProductRequest
{
    public string  Name  { get; set; } = string.Empty;
    public decimal Price { get; set; }
}

Wiring Everything Together in Program.cs

var builder = WebApplication.CreateBuilder(args);

// Register the full layer chain with DI
builder.Services.AddScoped<IProductRepository, InMemoryProductRepository>();
builder.Services.AddScoped<IProductService, ProductService>();
builder.Services.AddControllers();

var app = builder.Build();
app.MapControllers();
app.Run();

When a GET /api/products request arrives, ASP.NET Core:

  1. Creates a ProductsController, injecting an IProductService.
  2. To fulfil that, creates a ProductService, injecting an IProductRepository.
  3. To fulfil that, creates an InMemoryProductRepository.
  4. Calls GetAll() on the controller, which calls GetAllAsync() on the service, which calls GetAllAsync() on the repository.
  5. Results flow back up through the layers, being mapped to DTOs along the way, and are returned as JSON.
💡 Why the Repository Interface Matters

Because ProductService depends on IProductRepository (not InMemoryProductRepository directly), you can later swap the in-memory implementation for an Entity Framework Core implementation — without changing ProductService at all. One line in Program.cs changes and the entire application is now talking to a real database. This is the power of depending on abstractions.

📚 Key Terms

Controller Layer: Handles HTTP concerns — parsing input, calling services, returning responses. Contains no business logic.

Service Layer: Contains all business logic, validation rules, and orchestration. Depends on repositories and other services.

Repository Layer: Abstracts data access. Provides CRUD operations on domain entities. Knows about the database; knows nothing about HTTP or business rules.

DTO (Data Transfer Object): A plain class designed for sending or receiving data over an API. Shaped for the caller's needs, not the internal data model.

Separation of Concerns: The principle that each component should have one clearly defined responsibility and know as little as possible about the others.

Chapter Summary

  • Layered architecture separates your application into Controller, Service, and Repository layers — each with a single responsibility.
  • The Controller handles HTTP and nothing else. It calls the service and maps results to responses.
  • The Service layer contains business logic and orchestration. It calls repositories to get/store data.
  • The Repository layer abstracts data access. It exposes a clean interface so the service doesn't depend on a specific database technology.
  • All three layers depend on interfaces, not concrete classes — making them swappable and testable independently.
  • DTOs separate your internal domain model from your external API contract, protecting internal details and allowing them to evolve independently.
  • Everything is wired together through DI in Program.cs — one line per layer.
