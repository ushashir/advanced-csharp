Entity Framework Core — The Smart Librarian

Most applications need to persist data — and in the real world, that means a relational database. Entity Framework Core is the official .NET ORM that lets you work with databases using C# objects and LINQ, rather than writing raw SQL. It is powerful, flexible, and deeply integrated with ASP.NET Core.

What you'll learn in this chapter

  • What an ORM is and the problem it solves
  • DbContext as the bridge between your code and the database
  • Defining entities — plain C# classes that become database tables
  • DbSet<T> — your typed access point to each table
  • LINQ queries on DbContext
  • Migrations: Add-Migration and Update-Database
  • Relationships: one-to-many with navigation properties
  • Async database queries: ToListAsync, FirstOrDefaultAsync
  • Basic CRUD operations with EF Core

The Smart Librarian Analogy

Imagine a vast library with millions of books, all organized in a filing system only the librarian understands. You don't need to know the Dewey Decimal system, the layout of the stacks, or how books are indexed. You simply walk up to the librarian and say: "I'd like all the science-fiction books published after 2010, sorted by rating." The librarian disappears into the stacks and comes back with exactly what you asked for.

If the library needs to reorganise — say, adding a new wing for graphic novels — the librarian handles it (a migration). If you want to add a new book, you hand it to the librarian and they file it in the right place. You never touch the filing system yourself.

📚 The Smart Librarian

Entity Framework Core is the librarian. The library is your database. The books are your data rows. You describe what you want in C# and LINQ — "give me all Posts where BlogId equals 1, ordered by date" — and EF Core translates that into SQL, sends it to the database, and hands you back the results as C# objects. You never write SELECT * FROM Posts WHERE BlogId = 1 ORDER BY CreatedAt yourself (though EF Core generates exactly that under the hood).

What is an ORM?

ORM stands for Object-Relational Mapper. It bridges two different worlds: the object-oriented world of your C# code (where data lives in classes with properties and relationships) and the relational world of your database (where data lives in tables with rows, columns, and foreign keys).

Without an ORM, you would write raw ADO.NET code like:

// Without EF Core — raw ADO.NET
using var conn = new SqlConnection(connectionString);
await conn.OpenAsync();
using var cmd = conn.CreateCommand();
cmd.CommandText = "SELECT Id, Title FROM Blogs WHERE IsPublished = 1";
using var reader = await cmd.ExecuteReaderAsync();
var blogs = new List<Blog>();
while (await reader.ReadAsync())
{
    blogs.Add(new Blog { Id = reader.GetInt32(0), Title = reader.GetString(1) });
}

With EF Core, that same query is three lines of expressive LINQ. No SQL strings, no manual mapping, no column index arithmetic.

Defining Your Entities

In EF Core, a database table is represented by a C# class called an entity. Entity classes are plain C# objects (POCOs — Plain Old CLR Objects). EF Core uses conventions and configuration to map them to tables and columns. 

// Blog entity — maps to the "Blogs" table by convention
public class Blog
{
    public int    Id    { get; set; }       // primary key (by convention)
    public string Title { get; set; } = string.Empty;
    public string Url   { get; set; } = string.Empty;

    // Navigation property — one Blog has many Posts
    public List<Post> Posts { get; set; } = new();
}

// Post entity — maps to the "Posts" table
public class Post
{
    public int      Id        { get; set; }
    public string   Title     { get; set; } = string.Empty;
    public string   Content   { get; set; } = string.Empty;
    public DateTime CreatedAt { get; set; }

    // Foreign key — links this post to its blog
    public int  BlogId { get; set; }
    public Blog Blog   { get; set; } = null!;  // navigation property back to Blog
}

DbContext — The Bridge

DbContext is the central class in EF Core. It represents a session with the database. You subclass it, declare a DbSet<T> property for each entity, and EF Core handles the rest: tracking changes, generating SQL, managing connections. 

public class AppDbContext : DbContext
{
    public AppDbContext(DbContextOptions<AppDbContext> options)
        : base(options) { }

    // Each DbSet<T> represents a table
    public DbSet<Blog> Blogs { get; set; }
    public DbSet<Post> Posts { get; set; }
}

Registering EF Core in Program.cs

var builder = WebApplication.CreateBuilder(args);

// Register AppDbContext with SQL Server
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(builder.Configuration.GetConnectionString("DefaultConnection")));

// Or with SQLite (great for development and learning)
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlite("Data Source=app.db"));

Migrations — Evolving Your Database Schema

When you add or change entity classes, your database schema needs to change to match. EF Core migrations handle this for you. They generate C# files that describe the schema changes, and then apply those changes to the database. 

# Install the EF Core tools (once per machine)
dotnet tool install --global dotnet-ef

# Create a new migration — EF compares your entities to the current schema
dotnet ef migrations add InitialCreate

# Apply all pending migrations to the database
dotnet ef database update

# Add a migration after changing an entity
dotnet ef migrations add AddPostPublishedDate

# Roll back to a previous migration
dotnet ef database update PreviousMigrationName

Migrations create a Migrations/ folder in your project with files like 20240115120000_InitialCreate.cs. These files should be committed to source control — they are the history of how your database schema evolved.

LINQ Queries on DbContext

// Injected via DI in a repository or service
private readonly AppDbContext _context;

// Get all blogs
List<Blog> blogs = await _context.Blogs.ToListAsync();

// Get a single blog by ID
Blog? blog = await _context.Blogs.FirstOrDefaultAsync(b => b.Id == id);

// Get all posts for a specific blog
List<Post> posts = await _context.Posts
    .Where(p => p.BlogId == blogId)
    .OrderByDescending(p => p.CreatedAt)
    .ToListAsync();

// Include navigation properties (JOIN under the hood)
Blog? blogWithPosts = await _context.Blogs
    .Include(b => b.Posts)
    .FirstOrDefaultAsync(b => b.Id == id);

CRUD Operations

// CREATE — add a new blog
var newBlog = new Blog { Title = "My Blog", Url = "https://myblog.com" };
_context.Blogs.Add(newBlog);
await _context.SaveChangesAsync();   // SQL INSERT is executed here
// newBlog.Id is now populated with the database-generated ID

// READ — already shown above with ToListAsync / FirstOrDefaultAsync

// UPDATE — modify a tracked entity
var blog = await _context.Blogs.FindAsync(id);
if (blog is not null)
{
    blog.Title = "Updated Title";
    await _context.SaveChangesAsync(); // SQL UPDATE is executed here
}

// DELETE — remove a tracked entity
var toDelete = await _context.Blogs.FindAsync(id);
if (toDelete is not null)
{
    _context.Blogs.Remove(toDelete);
    await _context.SaveChangesAsync(); // SQL DELETE is executed here
}
💡 SaveChangesAsync is the Commit

EF Core tracks all changes you make to entities in memory — adds, modifications, deletions. None of them hit the database until you call SaveChangesAsync(). This is like a "commit" in a transaction. If multiple changes are needed and one fails, you can roll back them all by not calling SaveChangesAsync(). This unit-of-work behaviour is why DbContext is registered as Scoped — one per request, so all changes within a request are committed together.

🔎 What SQL Does EF Core Generate?

You can see the exact SQL EF Core generates by enabling logging. In development, add this to your DbContext options: options.LogTo(Console.WriteLine, LogLevel.Information). You will see statements like SELECT [b].[Id], [b].[Title], [b].[Url] FROM [Blogs] AS [b] printed to the console. This is invaluable for debugging performance and understanding what is actually happening.

📚 Key Terms

ORM (Object-Relational Mapper): A library that translates between C# objects and database tables, allowing you to work with data using objects and LINQ instead of SQL.

Entity: A C# class that maps to a database table. A row in the table is an instance of the class.

DbContext: The bridge between your C# code and the database. Manages entity tracking, SQL generation, and database connections.

DbSet<T>: A property on DbContext that represents a table. You query it with LINQ and add/remove entities through it.

Migration: A generated C# file that describes a database schema change. Applied with dotnet ef database update.

Navigation Property: A property on an entity that refers to a related entity or collection — the C# representation of a database foreign-key relationship.

SaveChangesAsync: Commits all tracked changes to the database in a single SQL transaction.

Chapter Summary

  • EF Core is an ORM — it maps C# objects (entities) to database tables and translates LINQ queries into SQL.
  • Entities are plain C# classes. By convention, a property named Id becomes the primary key.
  • DbContext is the bridge to the database. Subclass it and add a DbSet<T> for each entity.
  • Register DbContext as Scoped via builder.Services.AddDbContext<T>() — never as Singleton.
  • Migrations track schema changes over time. Use dotnet ef migrations add to create them and dotnet ef database update to apply them.
  • Use async query methods (ToListAsync, FirstOrDefaultAsync, FindAsync) to avoid blocking threads.
  • SaveChangesAsync() is the commit — no SQL is executed until you call it.
  • Use .Include() to eagerly load navigation properties (related entities) in the same query.
