Interfaces vs Abstract Classes — The Contract and the Parent

Both interfaces and abstract classes define rules that other types must follow. But they do it in different ways, for different reasons. Getting this distinction right is one of the most important design skills in object-oriented C# programming.

What you'll learn in this chapter

  • The core difference between interfaces and abstract classes
  • How to define an interface with properties and methods
  • How a class implements multiple interfaces (C# allows this)
  • Abstract class review and when to use it
  • Default interface methods (C# 8+)
  • A payment processing example using IPaymentProvider
  • Practical rules for choosing between the two
📋 The Contract and the Parent Analogy

An interface is like a job contract. When you sign a contract as a delivery driver, it specifies: you must deliver packages, you must obtain signatures, you must follow a route. The contract doesn't tell you how to drive, what vehicle to use, or how to pack your lunch. It only defines obligations.

An abstract class is like a family passing down traditions. A parent teaches children how the family cooks, how the family celebrates, what language they speak. The children inherit this foundation and can add their own twist — but they start from a shared, implemented base. The abstract methods are the things the parent says: "every child must do this — but each will do it their own way."

Rule of thumb: use an interface when you want to define a capability any class can gain. Use an abstract class when you want to share implementation code among related classes.

Defining an Interface

An interface is a pure contract — it declares what members a type must have, but provides no implementation (with one modern exception we'll cover shortly). Interface names conventionally start with I: 

public interface IPaymentProvider
{
    // Properties — no backing field, just a contract
    string ProviderName { get; }
    bool IsAvailable { get; }

    // Methods — signature only, no body
    Task<PaymentResult> ProcessPaymentAsync(PaymentRequest request);
    void RefundPayment(string transactionId);
}

public record PaymentRequest(decimal Amount, string Currency, string CardToken);
public record PaymentResult(bool Success, string TransactionId, string? ErrorMessage);

Implementing an Interface

A class implements an interface by listing it after the colon in the class declaration, then providing concrete implementations for every interface member: 

public class StripePaymentProvider : IPaymentProvider
{
    public string ProviderName => "Stripe";
    public bool IsAvailable => true;

    public async Task<PaymentResult> ProcessPaymentAsync(PaymentRequest request)
    {
        // Stripe-specific implementation
        await Task.Delay(100);  // simulate network call
        Console.WriteLine($"[Stripe] Processing £{request.Amount}");
        return new PaymentResult(true, $"stripe_{Guid.NewGuid():N}", null);
    }

    public void RefundPayment(string transactionId)
    {
        Console.WriteLine($"[Stripe] Refunding transaction {transactionId}");
    }
}

public class PayPalPaymentProvider : IPaymentProvider
{
    public string ProviderName => "PayPal";
    public bool IsAvailable => true;

    public async Task<PaymentResult> ProcessPaymentAsync(PaymentRequest request)
    {
        await Task.Delay(150);
        Console.WriteLine($"[PayPal] Processing £{request.Amount}");
        return new PaymentResult(true, $"pp_{Guid.NewGuid():N}", null);
    }

    public void RefundPayment(string transactionId)
    {
        Console.WriteLine($"[PayPal] Refunding {transactionId}");
    }
}

The power: any code that depends on IPaymentProvider works with either provider — or any new provider you add in future — without modification. This is the Open/Closed Principle in action.

Multiple Interface Implementation

C# classes can only inherit from one base class, but they can implement any number of interfaces. This is how C# achieves multiple inheritance of behaviour: 

public interface IPaymentProvider   { /* as above */ }
public interface ILoggable          { void Log(string message); }
public interface IHealthCheckable   { bool IsHealthy(); }

// One class, three contracts
public class StripePaymentProvider : IPaymentProvider, ILoggable, IHealthCheckable
{
    // Must implement all members of all three interfaces
    public string ProviderName => "Stripe";
    public bool IsAvailable => true;
    public async Task<PaymentResult> ProcessPaymentAsync(PaymentRequest r) => /* ... */;
    public void RefundPayment(string id) => /* ... */;

    public void Log(string message)
        => Console.WriteLine($"[Stripe LOG] {DateTime.UtcNow}: {message}");

    public bool IsHealthy()
    {
        // In real code: ping the Stripe API health endpoint
        return true;
    }
}

Abstract Class Review

An abstract class sits between a regular class and an interface. It can have:

  • Concrete (implemented) methods — shared by all subclasses
  • Abstract methods — each subclass must implement these its own way
  • Constructors, fields, and state — unlike interfaces
public abstract class ReportGenerator
{
    // Concrete — shared implementation
    public void GenerateReport(string title)
    {
        WriteHeader(title);
        WriteBody();       // abstract — subclass decides
        WriteFooter();
    }

    private void WriteHeader(string title)
        => Console.WriteLine($"=== {title} ===");

    private void WriteFooter()
        => Console.WriteLine("=== End of Report ===");

    // Abstract — must be implemented by each subclass
    protected abstract void WriteBody();
}

public class SalesReport : ReportGenerator
{
    protected override void WriteBody()
        => Console.WriteLine("Sales data: Q1 £45,000 | Q2 £52,000 | Q3 £48,000");
}

public class InventoryReport : ReportGenerator
{
    protected override void WriteBody()
        => Console.WriteLine("Items in stock: 1,240 | Low stock alerts: 12");
}

Default Interface Methods (C# 8+)

Since C# 8, interfaces can have default method implementations. This is useful for adding new methods to an interface without breaking every class that already implements it: 

public interface IPaymentProvider
{
    string ProviderName { get; }
    Task<PaymentResult> ProcessPaymentAsync(PaymentRequest request);
    void RefundPayment(string transactionId);

    // Default implementation — classes can override but don't have to
    string GetSupportUrl()
        => $"https://support.{ProviderName.ToLower()}.com";
}
💡 Use Default Interface Methods Sparingly

Default interface methods are primarily a versioning tool — they let library authors add new members to a public interface without a breaking change. In new code, it is usually cleaner to put shared logic in an abstract class or a static helper method. Do not use default interface methods as a substitute for abstract class inheritance.

When to Use Each

Here is a practical decision guide:

Use an INTERFACE when: Use an ABSTRACT CLASS when: ------------------------------------------+------------------------------------------ You want a capability contract | You want to share implementation code (IDisposable, IComparable, IPayable) | among related classes | A class needs to satisfy multiple | There is a genuine "is-a" relationship different contracts at once | (e.g. SalesReport IS-A ReportGenerator) | You don't own the implementing classes | You need constructors, fields, or state (they may be in other assemblies) | in the base type | The implementing classes are unrelated | All subclasses share a significant amount (e.g. string, FileStream, Button | of common logic can all be IDisposable) |
🎓 The Famous Design Maxim

"Program to an interface, not an implementation." — Gang of Four, Design Patterns (1994)

This quote is about interfaces in the general sense — designing your code to depend on contracts rather than concrete classes. In C#, this means your services should accept IPaymentProvider as a parameter, not StripePaymentProvider. Doing so makes your code testable (you can inject a mock), extensible (you can swap providers), and loosely coupled. This is the foundation of Dependency Injection, which you will learn in Part 3.

📚 Key Terms

Interface: A pure contract — defines what a type must do, not how. Declared with the interface keyword. No state, no implementation (except default methods in C# 8+).

Abstract class: A partial implementation — can have both abstract (contract-only) and concrete (implemented) members. Cannot be instantiated directly.

IDisposable: The most commonly implemented .NET interface — a single method Dispose(). Any type that manages resources (files, database connections) should implement it.

Multiple interface implementation: A class can implement any number of interfaces — this is C#'s way of achieving multiple inheritance without the ambiguity problems.

Default interface method: A method in an interface that provides a default body (C# 8+). Implementing classes can override it or use the default.

Chapter Summary

  • An interface is a contract — it defines what a type must do, but not how. Use it for capabilities and behavioural contracts.
  • An abstract class is a parent with some pre-built behaviour. Use it when related classes share significant implementation.
  • A class can implement many interfaces, but can only inherit from one base class.
  • Default interface methods (C# 8+) allow adding new methods to an interface without breaking existing implementations.
  • The convention: interface names start with I (IPaymentProvider, IDisposable, IComparable).
  • "Program to an interface, not an implementation" — this principle drives Dependency Injection (Part 3).

Exercise 10.2 — Code Challenge: Notification System

Design a notification system using an interface. Create:

  • INotificationSender — methods: Send(string recipient, string subject, string body) and property SenderName
  • EmailSender — implements the interface, prints an email-style message
  • SmsSender — implements the interface, prints an SMS-style message (no subject, truncate body to 160 chars)
  • PushNotificationSender — implements the interface, prints a push-style notification

Write a NotificationService that takes INotificationSender in its constructor and has a method Notify(string recipient, string subject, string body). Show that swapping the sender requires zero changes to NotificationService.

Exercise 10.3 — Design Decision

You are designing a game with these character types: Warrior, Mage, and Archer. All of them can Move(), Attack(), and have Health and Name properties. Warriors and Mages can both UseSpecialAbility(), but Archers cannot. All characters except Mages can EquipArmour().

Design the type hierarchy for this system. What should be an abstract class? What should be interfaces? Justify each decision. You do not need to write full implementation code — just the declarations.
