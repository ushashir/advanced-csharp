Validation — The Form Checker

Never trust user input. It is one of the oldest rules in software development, and for good reason. Data validation — ensuring that what the client sends actually meets your requirements before you process it — is the first line of defence against bad data, bugs, and security vulnerabilities.

What you'll learn in this chapter

  • Data Annotations: [Required], [StringLength], [EmailAddress], [Range], [RegularExpression]
  • How ASP.NET Core's automatic model validation works with ModelState
  • Returning a 400 Bad Request with validation errors
  • FluentValidation as a more powerful alternative — AbstractValidator<T> and RuleFor()
  • Registering FluentValidation validators with dependency injection
  • Async validation — checking against a database during validation
  • A complete CreateUserRequest DTO with both approaches

The Airline Check-in Agent

Picture yourself at an airport check-in desk. Before the agent lets you through to the departure gate, they check everything methodically: Is your passport valid and not expired? Does your name on the ticket match your passport? Is your bag within the weight limit? Do you have a valid boarding pass for this flight? Only when every single rule passes do they hand back your documents and wave you through.

If your bag is overweight, they don't just take your passport and wave you on anyway — the whole process stops. You fix the problem first, then you can proceed. No partial passes. All rules must pass.

That is input validation in your API. Before your controller calls any service, before you touch the database — the incoming request must pass every validation rule, or it stops at the door with a 400 Bad Request.

✈️ The Check-in Agent Analogy

The passenger = incoming HTTP request body.
The check-in rules = Data Annotations or FluentValidation rules.
The 400 Bad Request = "You can't proceed. Fix these problems first."
The validation error list = The agent's checklist of what needs fixing.

The agent doesn't decide which rules to enforce on a case-by-case basis — the rules are defined in advance and applied consistently to every passenger. Your validators should work the same way: defined once, applied automatically.

Approach 1: Data Annotations

Data Annotations are attributes you place directly on your DTO (Data Transfer Object) properties. ASP.NET Core reads these automatically and validates incoming request bodies before your action method runs. 

using System.ComponentModel.DataAnnotations;

public class CreateUserRequest
{
    [Required(ErrorMessage = "First name is required.")]
    [StringLength(50, MinimumLength = 2, ErrorMessage = "First name must be between 2 and 50 characters.")]
    public string FirstName { get; set; } = "";

    [Required(ErrorMessage = "Last name is required.")]
    [StringLength(50, MinimumLength = 2, ErrorMessage = "Last name must be between 2 and 50 characters.")]
    public string LastName { get; set; } = "";

    [Required(ErrorMessage = "Email is required.")]
    [EmailAddress(ErrorMessage = "Email must be a valid email address.")]
    [StringLength(256)]
    public string Email { get; set; } = "";

    [Required(ErrorMessage = "Password is required.")]
    [StringLength(100, MinimumLength = 8, ErrorMessage = "Password must be at least 8 characters.")]
    [RegularExpression(@"^(?=.*[A-Z])(?=.*\d).+$",
        ErrorMessage = "Password must contain at least one uppercase letter and one number.")]
    public string Password { get; set; } = "";

    [Range(13, 120, ErrorMessage = "Age must be between 13 and 120.")]
    public int Age { get; set; }

    [Url(ErrorMessage = "Profile picture URL must be a valid URL.")]
    public string? ProfilePictureUrl { get; set; }
}

Available Data Annotation Attributes

  • [Required] — The property must not be null or empty.
  • [StringLength(max, MinimumLength = min)] — String length constraints.
  • [EmailAddress] — Must be a valid email format.
  • [Range(min, max)] — Numeric value must be within a range.
  • [RegularExpression(pattern)] — Must match a regex pattern.
  • [MinLength(n)] / [MaxLength(n)] — Collection or string length limits.
  • [Url] — Must be a valid absolute URL.
  • [Phone] — Must be a valid phone number format.
  • [Compare("OtherProperty")] — Must equal another property (e.g., ConfirmPassword must equal Password).
  • [CreditCard] — Must be a valid credit card number format.

Automatic Model Validation in ASP.NET Core

When you decorate your DTO with Data Annotations, ASP.NET Core validates it automatically before your action method runs. The result goes into ModelState: 

[ApiController]
[Route("api/users")]
public class UsersController : ControllerBase
{
    [HttpPost]
    public IActionResult CreateUser([FromBody] CreateUserRequest request)
    {
        // With [ApiController], this check is automatic — ASP.NET Core
        // returns 400 before this code even runs if validation fails.
        // But you can also check manually:
        if (!ModelState.IsValid)
            return ValidationProblem(ModelState);

        // If we get here, request is valid
        return Created($"/api/users/new-id", new { Message = "User created" });
    }
}
💡 [ApiController] Handles Validation Automatically

If your controller has the [ApiController] attribute, ASP.NET Core automatically returns a 400 Bad Request with a Problem Details body when ModelState.IsValid is false — without you needing to write the check. The manual if (!ModelState.IsValid) check is only needed in controllers without [ApiController], such as MVC controllers rendering views.

The automatic validation error response looks like:

{
  "type": "https://tools.ietf.org/html/rfc7231#section-6.5.1",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "errors": {
    "Email": ["Email must be a valid email address."],
    "Password": [
      "Password must be at least 8 characters.",
      "Password must contain at least one uppercase letter and one number."
    ]
  }
}

Approach 2: FluentValidation — Validation Without Clutter

Data Annotations are convenient, but they have limits. Complex validation rules — especially those involving multiple properties, conditional logic, or async database checks — become unwieldy as attributes. FluentValidation is a popular library that moves validation rules into a dedicated class, keeping your DTOs clean. 

dotnet add package FluentValidation.AspNetCore

Here is the same CreateUserRequest validated with FluentValidation:

using FluentValidation;

public class CreateUserRequestValidator : AbstractValidator<CreateUserRequest>
{
    private readonly IUserRepository _userRepo;

    public CreateUserRequestValidator(IUserRepository userRepo)
    {
        _userRepo = userRepo;

        RuleFor(x => x.FirstName)
            .NotEmpty().WithMessage("First name is required.")
            .Length(2, 50).WithMessage("First name must be between 2 and 50 characters.");

        RuleFor(x => x.LastName)
            .NotEmpty().WithMessage("Last name is required.")
            .Length(2, 50);

        RuleFor(x => x.Email)
            .NotEmpty()
            .EmailAddress().WithMessage("Must be a valid email address.")
            .MaximumLength(256)
            // Async rule: check if email is already taken
            .MustAsync(async (email, cancellationToken) =>
                !await _userRepo.EmailExistsAsync(email))
            .WithMessage("This email address is already registered.");

        RuleFor(x => x.Password)
            .NotEmpty()
            .MinimumLength(8).WithMessage("Password must be at least 8 characters.")
            .Matches(@"[A-Z]").WithMessage("Password must contain at least one uppercase letter.")
            .Matches(@"\d").WithMessage("Password must contain at least one number.");

        RuleFor(x => x.Age)
            .InclusiveBetween(13, 120).WithMessage("Age must be between 13 and 120.");

        // Conditional rule: only validate URL if it is provided
        RuleFor(x => x.ProfilePictureUrl)
            .Must(url => Uri.TryCreate(url, UriKind.Absolute, out _))
            .WithMessage("Profile picture URL must be a valid URL.")
            .When(x => x.ProfilePictureUrl != null);
    }
}

Registering FluentValidation Validators

using FluentValidation;

// Option 1: Register manually
builder.Services.AddScoped<IValidator<CreateUserRequest>, CreateUserRequestValidator>();

// Option 2: Auto-register all validators in an assembly (recommended)
builder.Services.AddValidatorsFromAssemblyContaining<CreateUserRequestValidator>();

Using FluentValidation in a Controller

[HttpPost]
public async Task<IActionResult> CreateUser(
    [FromBody] CreateUserRequest request,
    [FromServices] IValidator<CreateUserRequest> validator)
{
    var result = await validator.ValidateAsync(request);

    if (!result.IsValid)
    {
        var errors = result.Errors
            .GroupBy(e => e.PropertyName)
            .ToDictionary(
                g => g.Key,
                g => g.Select(e => e.ErrorMessage).ToArray());

        return ValidationProblem(new ValidationProblemDetails(errors));
    }

    // Validation passed — proceed with creating the user
    return Created("/api/users/1", new { Message = "User created successfully." });
}

Data Annotations vs FluentValidation — When to Use Which?

  • Use Data Annotations for simple, self-contained rules that are intrinsic to the DTO itself (required, string length, email format). They are fast to write and automatically enforced by the ASP.NET Core framework.
  • Use FluentValidation when rules are complex (multiple properties, conditional logic), when you need async validation (database lookups), when the same DTO needs different validation in different contexts, or when you want to keep DTOs clean and separate validation into its own testable class.
  • Mixing them is fine — Data Annotations for the basics, FluentValidation for the advanced cases.
🔬 Why Data Annotations Have Limits

Consider this rule: "If the user selects 'Corporate' as account type, then a company registration number is required." This cross-property conditional logic is nearly impossible to express cleanly with Data Annotations. With FluentValidation it's one readable line: 

RuleFor(x => x.CompanyRegistrationNumber)
    .NotEmpty()
    .When(x => x.AccountType == "Corporate");
📚 Key Terms Summary

Data Annotations: Attributes in System.ComponentModel.DataAnnotations that declare validation rules directly on DTO properties.

ModelState: An ASP.NET Core dictionary that records validation results for the current request. ModelState.IsValid returns false if any rule failed.

FluentValidation: A popular .NET library that defines validation rules in a separate class inheriting from AbstractValidator<T>.

AbstractValidator<T>: The base class for FluentValidation validators. Override the constructor to add rules with RuleFor().

MustAsync(): A FluentValidation method for async validation rules — useful for checking a value against a database.

Chapter Summary

  • Validate all incoming data before it reaches your business logic — never trust client input.
  • Data Annotations ([Required], [StringLength], [EmailAddress], [Range], [RegularExpression]) are the built-in approach, applied as attributes on DTO properties.
  • ASP.NET Core with [ApiController] automatically validates the model and returns 400 Bad Request with error details if validation fails.
  • FluentValidation provides a more powerful, testable alternative using AbstractValidator<T> and a fluent RuleFor() API.
  • FluentValidation supports async rules (MustAsync) and conditional rules (When), making it ideal for complex validation scenarios.
  • Register validators with AddValidatorsFromAssemblyContaining<T>() for automatic discovery.
  • Both approaches produce 400 Bad Request responses with structured error details — consistent and parseable by any client.
