Part 4 Exercises — ASP.NET Core Advanced

These exercises cover the four advanced topics from Part 4: authentication & authorization, JWT, exception handling, validation, and microservices. Work through them at your own pace. Some are quick quiz questions; others are design challenges that require deeper thinking.

What these exercises cover

  • Authentication vs Authorization — distinguishing the concepts in real scenarios
  • JWT anatomy and claims — reading and creating tokens
  • Global exception handling — designing a production-ready error system
  • Validation — applying Data Annotations and FluentValidation
  • Microservices — architecture decisions and communication patterns
  • Security review — spotting vulnerabilities in code
  • Building a protected endpoint from scratch
  • Reflection — honest thinking about when not to use microservices
Exercise P4.1 — AuthN vs AuthZ Scenarios

For each of the following events, label it as Authentication (AuthN), Authorization (AuthZ), or Both, and explain your reasoning:

  1. A user types their email and password on the login page.
  2. A user is prevented from deleting another user's post because they are not an Admin.
  3. A user's JWT has expired and they are redirected to the login page.
  4. A user passes 2FA verification and gains access to their account.
  5. A user with role "Editor" tries to access the admin dashboard and receives 403 Forbidden.
  6. An API key is sent in the X-Api-Key header and the server validates it.
Exercise P4.2 — JWT Claims Challenge

You are building a multi-tenant SaaS application. Each user belongs to exactly one company (tenant). Design the claims that your JWT should contain to support:

  • Identifying the user (user ID and email)
  • Identifying which company they belong to (tenant ID and tenant name)
  • Their role within that company (Owner, Admin, Member, ReadOnly)
  • Whether their account is on a free or paid plan
  • When the token expires

Write out a sample JWT payload as a JSON object with these claims. Use sensible claim names (following the sub, email convention where appropriate, and custom short names for the rest).

Exercise P4.3 — Design a Global Exception Handler

A logistics company's API throws the following exceptions throughout its codebase. For each exception, determine the appropriate HTTP status code and a sensible Problem Details title and detail message:

  • ShipmentNotFoundException — when a tracking number doesn't match any shipment
  • AddressValidationException — when a delivery address fails postal validation
  • CarrierUnavailableException — when an external carrier API is down
  • DuplicateTrackingNumberException — when a tracking number is already in the system
  • InsufficientFundsException — when an account doesn't have enough credit

Then write the GlobalExceptionHandler.TryHandleAsync() switch expression that maps all five exceptions to their HTTP status codes.

Exercise P4.4 — Validation Annotations

Write a CreateOrderRequest DTO with Data Annotation validation for an e-commerce order. The order must have:

  • A CustomerId: required, positive integer
  • A DeliveryAddress: required, 10–500 characters
  • A ContactEmail: required, valid email, max 256 characters
  • A ContactPhone: optional, valid phone number if provided
  • A RequestedDeliveryDate: optional, must be in the future if provided (use [DataType(DataType.Date)])
  • An Items list: required, must contain at least one item (use [MinLength(1)])

Also write the OrderItem sub-object with its own validation attributes.

Exercise P4.5 — Microservices Architecture Question

A social media platform has the following features: user profiles, posts, comments, likes, followers, private messages, notifications, search, and image processing.

Which features would you consider as candidates for separate microservices? Which would you keep together? For each candidate service you propose, explain:

  • Why it warrants being its own service (what boundary justifies it?)
  • What its single responsibility is
  • How it would communicate with the other services you've identified

Draw a simple text diagram showing the services and their communication relationships.

Exercise P4.6 — Security Review Checklist

Review the following Program.cs configuration and identify every security problem. There are at least seven. For each one, explain the risk and how to fix it. 

var builder = WebApplication.CreateBuilder(args);

builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = false,
            ValidateAudience = false,
            ValidateLifetime = false,
            IssuerSigningKey = new SymmetricSecurityKey(
                Encoding.UTF8.GetBytes("abc"))
        };
    });

var app = builder.Build();

app.UseAuthorization();
app.UseAuthentication();

app.MapControllers();
app.Run();
Exercise P4.7 — Code a Protected Endpoint

Build a complete mini-API (can be a single file using ASP.NET Core Minimal APIs) with the following:

  • A POST /auth/login endpoint that accepts { "email": "...", "password": "..." } and returns a JWT on success, 401 on failure
  • A GET /profile endpoint protected by [Authorize] that returns the user's claims from the JWT
  • A GET /admin/stats endpoint that requires the "Admin" role
  • FluentValidation on the login request (email must be a valid email, password must not be empty)
  • A GlobalExceptionHandler that handles any exceptions not caught elsewhere

This is a full integration exercise — put everything from Chapters 20–23 together. Test it with curl or a REST client.

Exercise P4.8 — Reflection: When NOT to Use Microservices

The chapter argued that you should not default to microservices for every new project. Write a 3–4 paragraph reflection on the following:

  • Describe a real or hypothetical project where a monolith is clearly the right choice. Justify your reasoning.
  • Describe a real or hypothetical project where microservices would genuinely add value. What specific characteristics make the difference?
  • What is the "distributed monolith" anti-pattern? How can you tell if a microservices architecture has become one?
  • If you were joining a company that already has a large monolith that is struggling, what criteria would you use to decide which parts to extract first as microservices?

There is no single correct answer here — this is a design thinking exercise. The goal is to demonstrate nuanced understanding of the trade-offs.

Part 4 Summary — What You Have Learned

  • Chapter 20: Authentication (who are you?) and Authorization (what can you do?) are separate concerns. [Authorize], roles, claims, and policies control access in ASP.NET Core. Middleware order — UseAuthentication before UseAuthorization — is critical.
  • Chapter 21: JWTs are stateless tokens with three parts (header.payload.signature). Configure JWT Bearer authentication with TokenValidationParameters, generate tokens with JwtSecurityTokenHandler, and always protect the secret key.
  • Chapter 22: Global exception handling via IExceptionHandler and UseExceptionHandler() gives consistent, secure error responses. Use Problem Details (RFC 7807), log everything internally, and never expose stack traces to clients.
  • Chapter 23: Validate all input at the door. Data Annotations for simple rules; FluentValidation for complex, conditional, and async validation. [ApiController] makes validation automatic.
  • Chapter 24: Microservices provide independent deployment and scaling at the cost of significant complexity. Use IHttpClientFactory for typed HTTP clients, Polly for resilience, and message queues for asynchronous communication. Don't reach for microservices before you need them.
