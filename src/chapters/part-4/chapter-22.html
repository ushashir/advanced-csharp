Part 4 · Chapter 22

Exception Handling Middleware — The Error Department

Errors are inevitable. Databases go down, files go missing, services time out. How your application handles those errors — consistently, informatively, and without leaking internal details — is the mark of professional software. ASP.NET Core 8 gives you a clean, standardised way to manage this: global exception handling with Problem Details.

What you'll learn in this chapter

  • Why global exception handling matters (consistency, security, user experience)
  • The IExceptionHandler interface (ASP.NET Core 8+)
  • Problem Details — the RFC 7807 standard for HTTP error responses
  • Creating a custom GlobalExceptionHandler
  • Mapping specific exception types to HTTP status codes
  • Logging exceptions properly — what to log and what not to expose
  • The complete pattern: custom exceptions + handler + Problem Details

The Company Complaints Department

Imagine a large company where every employee handles customer complaints in their own way. One person apologises profusely and gives away free products. Another sends a terse one-line email. A third accidentally shares internal company secrets in their reply. The result is chaotic, inconsistent, and sometimes embarrassing.

A good company has a dedicated complaints department — a single, professional team that handles all problems with a consistent process: acknowledge the issue, explain what went wrong at an appropriate level of detail, offer a resolution, and log the incident for review. Customers always receive the same professional response.

That is exactly what a global exception handler is in ASP.NET Core. Instead of every controller and service handling errors differently, a single piece of middleware intercepts all unhandled exceptions and converts them into consistent, professional responses.

🏢 The Complaints Department Analogy

Without global exception handling: each controller catches (or doesn't catch) exceptions in its own way. Some return plain text. Some return HTML. Some accidentally include stack traces with file paths and class names — giving attackers a map of your internals.

With global exception handling: every unhandled exception flows to a single handler. The handler logs the full details (for your team), translates the exception into an appropriate HTTP status code, and returns a clean, standardised error response to the client — with no internal details exposed.

Why Not Just Try/Catch Everywhere?

You could wrap every controller action in a try/catch block. Many beginners do. But this approach has serious problems:

  • Repetition: You write the same error-handling code in dozens of places, and inevitably they diverge over time.
  • Inconsistency: Action A returns { "error": "not found" }; Action B returns a plain 404 string. Your API clients never know what format to expect.
  • Missed exceptions: If you forget to add a try/catch, ASP.NET Core returns a raw 500 with a stack trace — leaking your application internals.
  • Cross-cutting concern: Exception handling is infrastructure — it should live at the infrastructure level, not scattered through business logic.

Problem Details — RFC 7807 Standard

Before we write the handler, let's understand the response format. ASP.NET Core supports Problem Details, the standardised JSON format for HTTP error responses defined in RFC 7807. It looks like this: 

{
  "type": "https://tools.ietf.org/html/rfc7231#section-6.5.4",
  "title": "Not Found",
  "status": 404,
  "detail": "User with ID 99 was not found.",
  "instance": "/api/users/99",
  "traceId": "0HN7RK3FQPV1A:00000001"
}

This format is recognised by API clients worldwide and is the standard that modern .NET applications use. ASP.NET Core 8 makes it easy to produce this format automatically.

Custom Exception Types

The first step in a clean exception handling strategy is defining your own exception hierarchy — specific exception types that carry semantic meaning: 

// Base application exception
public abstract class AppException : Exception
{
    public int StatusCode { get; }
    protected AppException(string message, int statusCode) : base(message)
        => StatusCode = statusCode;
}

// 404 — resource does not exist
public class NotFoundException : AppException
{
    public NotFoundException(string resourceName, object key)
        : base($"{resourceName} with key '{key}' was not found.", 404) { }
}

// 400 — client sent invalid data
public class ValidationException : AppException
{
    public IDictionary<string, string[]> Errors { get; }

    public ValidationException(IDictionary<string, string[]> errors)
        : base("One or more validation errors occurred.", 400)
        => Errors = errors;
}

// 403 — authenticated but not permitted
public class ForbiddenException : AppException
{
    public ForbiddenException(string message = "You do not have permission to perform this action.")
        : base(message, 403) { }
}

// 409 — resource conflict
public class ConflictException : AppException
{
    public ConflictException(string message) : base(message, 409) { }
}

Now your service layer can be expressive and clean:

public async Task<UserDto> GetUserByIdAsync(int id)
{
    var user = await _context.Users.FindAsync(id);

    // No try/catch needed — just throw the right exception
    if (user is null)
        throw new NotFoundException(nameof(User), id);

    return user.ToDto();
}

The Global Exception Handler (ASP.NET Core 8+)

ASP.NET Core 8 introduced the IExceptionHandler interface — a clean, typed way to handle exceptions globally. Here is a full implementation: 

using Microsoft.AspNetCore.Diagnostics;
using Microsoft.AspNetCore.Mvc;

public class GlobalExceptionHandler : IExceptionHandler
{
    private readonly ILogger<GlobalExceptionHandler> _logger;

    public GlobalExceptionHandler(ILogger<GlobalExceptionHandler> logger)
        => _logger = logger;

    public async ValueTask<bool> TryHandleAsync(
        HttpContext httpContext,
        Exception exception,
        CancellationToken cancellationToken)
    {
        // Log every exception — full details for our team
        _logger.LogError(exception,
            "Unhandled exception on {Method} {Path}",
            httpContext.Request.Method,
            httpContext.Request.Path);

        // Map exception type to status code and title
        var (statusCode, title) = exception switch
        {
            NotFoundException e    => (404, "Not Found"),
            ValidationException e  => (400, "Validation Error"),
            ForbiddenException e   => (403, "Forbidden"),
            ConflictException e    => (409, "Conflict"),
            AppException e         => (e.StatusCode, "Application Error"),
            _                       => (500, "Internal Server Error")
        };

        // Build a Problem Details response
        var problemDetails = new ProblemDetails
        {
            Status   = statusCode,
            Title    = title,
            Detail   = exception.Message,
            Instance = httpContext.Request.Path
        };

        // Add validation errors if applicable
        if (exception is ValidationException valEx)
            problemDetails.Extensions["errors"] = valEx.Errors;

        httpContext.Response.StatusCode = statusCode;
        httpContext.Response.ContentType = "application/problem+json";

        await httpContext.Response.WriteAsJsonAsync(problemDetails, cancellationToken);

        // Return true = we handled it; false = pass to next handler
        return true;
    }
}

Registering the Handler

var builder = WebApplication.CreateBuilder(args);

// Register the handler and enable Problem Details
builder.Services.AddExceptionHandler<GlobalExceptionHandler>();
builder.Services.AddProblemDetails();
builder.Services.AddControllers();

var app = builder.Build();

// UseExceptionHandler must come early in the pipeline
app.UseExceptionHandler();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();

app.Run();

The Complete Error Flow in Action

Here is the entire flow for a "GET /api/users/99" request when user 99 doesn't exist:

Client: GET /api/users/99 ↓ UsersController.GetById(99) ↓ UserService.GetUserByIdAsync(99) ↓ throw new NotFoundException("User", 99) ↓ GlobalExceptionHandler.TryHandleAsync() - Logs: "Unhandled exception on GET /api/users/99" - Maps NotFoundException → 404 - Builds ProblemDetails response ↓ Client receives: { "type": "...", "title": "Not Found", "status": 404, "detail": "User with key '99' was not found.", "instance": "/api/users/99" }
💡 What to Log vs What to Return

Log everything: Log the full exception including stack trace, using ILogger.LogError(exception, ...). Your operations team needs this to debug production issues.

Return only safe information: The client response should contain the HTTP status code, a human-readable title, and a safe detail message. Never return stack traces, file paths, SQL queries, or connection strings to the client — these are goldmines for attackers.

The Alternative: UseExceptionHandler with a Lambda (Pre .NET 8)

If you are on an older version of ASP.NET Core, the traditional approach uses a lambda inside UseExceptionHandler: 

app.UseExceptionHandler(errorApp =>
{
    errorApp.Run(async context =>
    {
        var exceptionFeature = context.Features.Get<IExceptionHandlerPathFeature>();
        var exception = exceptionFeature?.Error;

        var statusCode = exception is NotFoundException ? 404 : 500;

        context.Response.StatusCode = statusCode;
        context.Response.ContentType = "application/json";

        await context.Response.WriteAsJsonAsync(new
        {
            Status = statusCode,
            Message = exception?.Message ?? "An error occurred"
        });
    });
});
📚 Key Terms Summary

IExceptionHandler: An ASP.NET Core 8+ interface for building typed global exception handlers. Implement TryHandleAsync to intercept and respond to exceptions.

Problem Details (RFC 7807): The standard JSON format for HTTP API error responses, containing type, title, status, detail, and instance.

AddProblemDetails(): Registers the Problem Details services so ASP.NET Core can automatically produce RFC 7807-formatted error responses.

UseExceptionHandler(): Middleware that catches unhandled exceptions and routes them to registered exception handlers.

Chapter Summary

  • Global exception handling gives every request the same professional error response — consistent, informative, and secure.
  • Problem Details (RFC 7807) is the standard format for HTTP error responses: type, title, status, detail, instance.
  • Define a custom exception hierarchy (NotFoundException, ValidationException, etc.) to add semantic meaning to errors.
  • Implement IExceptionHandler with a TryHandleAsync method to map exception types to HTTP status codes and Problem Details responses.
  • Register with builder.Services.AddExceptionHandler<GlobalExceptionHandler>() and activate with app.UseExceptionHandler().
  • Log the full exception details server-side; return only safe information to the client.
  • UseExceptionHandler() must appear early in the middleware pipeline to catch exceptions from everything below it.
