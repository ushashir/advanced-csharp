Microservices — The City of Shops

Microservices is one of the most talked-about architectural patterns in software — and one of the most misunderstood. Before you split your application into dozens of tiny services, you need to understand both the power and the significant cost of this approach. Microservices are not always the answer.

What you'll learn in this chapter

  • Monolith vs microservices — honest trade-offs
  • When microservices make sense (and when they absolutely don't)
  • HTTP/REST service-to-service communication with HttpClient and IHttpClientFactory
  • Message queues — RabbitMQ and Azure Service Bus (concept introduction)
  • Service discovery and Docker containers (conceptual overview)
  • The real problems microservices introduce: distributed tracing, eventual consistency, network failures
  • Polly for resilient HTTP calls with retry policies

The Department Store vs The City of Shops

Imagine two ways to build a retail experience. The first is a department store — one giant building where you can buy clothes, electronics, food, and furniture all under one roof. Everything is managed by one organisation. The heating, the tills, the staff directory — all shared. If the building closes, you can't buy anything at all.

The second is a city of independent shops. There is a clothes shop, an electronics shop, a bakery, a furniture showroom. Each shop is owned and run independently. They communicate — the bakery might refer you to the café next door — but each has its own staff, its own systems, its own opening hours. If the electronics shop closes for renovations, the bakery stays open.

🏬 The Architecture Analogy

The monolith = The department store. One codebase, one deployment, one database. Everything is in one place. Simple to develop and run when small, but as it grows, it becomes hard to change — a renovation in the electronics section can disrupt the entire store.

Microservices = The city of shops. Multiple independent services, each with its own codebase, database, and deployment pipeline. Each "shop" does one thing well. If the OrderService needs an update, you deploy just that service — without touching the UserService or PaymentService. But coordinating communication between all the shops is complex and requires careful planning.

Monolith vs Microservices — The Honest Trade-offs

Monolith Advantages

  • Simple to develop — one codebase, one project, one database.
  • Simple to deploy — one artifact, one deployment pipeline.
  • Simple to debug — no network hops, no distributed tracing.
  • Excellent performance for internal calls — function calls, not HTTP requests.
  • Easier for small teams — less operational overhead.

Microservices Advantages

  • Independent deployment — deploy UserService without touching OrderService.
  • Independent scaling — scale the heavy PaymentService without scaling the lightweight NotificationService.
  • Technology freedom — each service can use a different language or framework.
  • Isolated failures — a crash in RecommendationService doesn't bring down the whole application.
  • Smaller codebases — easier for individual teams to own and understand.
⚠️ When NOT to Use Microservices

The microservices hype has led many teams to start with a distributed architecture before they even understand their domain. The result is often called a "distributed monolith" — you get all the complexity of microservices with none of the benefits. A good rule of thumb: start with a well-structured monolith. Split into services only when you have clear, stable boundaries and a genuine need to deploy or scale them independently. Netflix, Uber, and Amazon started as monoliths. They extracted services only when they had to.

Service-to-Service HTTP Communication

The most common way for .NET microservices to communicate is over HTTP/REST. ASP.NET Core provides IHttpClientFactory as the recommended way to create HTTP clients — it manages connection pooling, handles socket exhaustion, and integrates cleanly with DI.

📚 Key Term: IHttpClientFactory

An interface that manages the lifecycle of HttpClient instances, preventing socket exhaustion (a real production problem with new HttpClient()) and enabling features like named clients, typed clients, and middleware pipelines per client. Always use IHttpClientFactory instead of constructing HttpClient directly.

Named HttpClient

// Register a named client in Program.cs
builder.Services.AddHttpClient("OrderService", client =>
{
    client.BaseAddress = new Uri("https://order-service/");
    client.DefaultRequestHeaders.Add("Accept", "application/json");
    client.Timeout = TimeSpan.FromSeconds(30);
});

// Use it via injection
public class UserService
{
    private readonly IHttpClientFactory _httpClientFactory;

    public UserService(IHttpClientFactory httpClientFactory)
        => _httpClientFactory = httpClientFactory;

    public async Task<IEnumerable<OrderDto>> GetUserOrdersAsync(int userId)
    {
        var client = _httpClientFactory.CreateClient("OrderService");
        var response = await client.GetAsync($"/api/orders?userId={userId}");
        response.EnsureSuccessStatusCode();
        return await response.Content.ReadFromJsonAsync<IEnumerable<OrderDto>>()
            ?? Enumerable.Empty<OrderDto>();
    }
}

Typed HttpClient — Cleaner and More Testable

// A typed client encapsulates all calls to one downstream service
public class OrderServiceClient
{
    private readonly HttpClient _httpClient;

    public OrderServiceClient(HttpClient httpClient)
        => _httpClient = httpClient;

    public async Task<IEnumerable<OrderDto>> GetOrdersForUserAsync(int userId)
    {
        var response = await _httpClient.GetAsync($"/api/orders?userId={userId}");
        response.EnsureSuccessStatusCode();
        return await response.Content
            .ReadFromJsonAsync<IEnumerable<OrderDto>>()
            ?? Enumerable.Empty<OrderDto>();
    }
}

// Register the typed client in Program.cs
builder.Services.AddHttpClient<OrderServiceClient>(client =>
    client.BaseAddress = new Uri("https://order-service/"));

Resilience with Polly — Retry Policies

In a distributed system, network calls fail. A service might be temporarily unavailable, a database might be restarting, a network partition might cause a timeout. Polly is a .NET resilience library that makes it easy to add retry logic, circuit breakers, timeouts, and fallbacks to your HTTP calls. 

dotnet add package Microsoft.Extensions.Http.Polly
using Polly;

builder.Services
    .AddHttpClient<OrderServiceClient>(client =>
        client.BaseAddress = new Uri("https://order-service/"))
    // Retry up to 3 times with exponential back-off
    .AddTransientHttpErrorPolicy(policy =>
        policy.WaitAndRetryAsync(
            retryCount: 3,
            sleepDurationProvider: attempt => TimeSpan.FromSeconds(Math.Pow(2, attempt)),
            onRetry: (outcome, delay, attempt, context) =>
            {
                Console.WriteLine($"Retry {attempt} after {delay.TotalSeconds}s");
            }))
    // Circuit breaker: stop retrying after 5 failures in 30 seconds
    .AddTransientHttpErrorPolicy(policy =>
        policy.CircuitBreakerAsync(
            handledEventsAllowedBeforeBreaking: 5,
            durationOfBreak: TimeSpan.FromSeconds(30)));

Message Queues — Asynchronous Communication

Not all service communication needs to be synchronous (request/response). Sometimes you want one service to publish an event and have another service handle it in its own time — without the first service waiting. This is where message queues come in.

Without a message queue (synchronous): UserService → POST /api/emails → EmailService → waits for response With a message queue (asynchronous): UserService → publishes "UserRegistered" event → Message Queue ↓ EmailService picks it up and sends the email at its own pace UserService moves on immediately ← doesn't wait

Popular message brokers in the .NET ecosystem:

  • RabbitMQ — open-source, self-hosted, AMQP protocol. Use the MassTransit library for .NET integration.
  • Azure Service Bus — managed cloud message queue from Microsoft. Deep integration with Azure and .NET via the Azure.Messaging.ServiceBus package.
  • Apache Kafka — high-throughput distributed streaming platform. Use with Confluent.Kafka package.

The Problems Microservices Introduce

Microservices are not a free lunch. Every advantage comes with a corresponding challenge. Be honest about these costs before committing to the architecture:

  • Distributed tracing: When a request flows through 5 services and something fails, which service caused the error? You need distributed tracing tools (OpenTelemetry, Jaeger, Zipkin) and correlation IDs on every request.
  • Eventual consistency: When UserService updates a user's email and then OrderService needs to display it — how long until OrderService has the new value? Distributed systems cannot guarantee strong consistency without sacrificing availability.
  • Network failures: Internal function calls never fail due to network issues. HTTP calls between services can. Timeouts, connection refused, DNS failures — you must plan for all of these. That is why resilience libraries like Polly are essential.
  • Operational complexity: Instead of deploying one application, you now manage 10+ Docker containers, a service registry, a message broker, multiple databases, and a distributed tracing system. You will need Kubernetes or at least Docker Compose.
  • Testing difficulty: Unit-testing a monolith is straightforward. Integration-testing a distributed system requires spinning up multiple services, databases, and message brokers. End-to-end tests become slow and flaky.

Docker — The Container for Your Shop

Microservices and Docker are natural partners. Docker packages each service into a self-contained container with everything it needs to run: the .NET runtime, the compiled code, configuration. A container runs identically on your laptop, a colleague's machine, and a cloud server. 

# A minimal Dockerfile for an ASP.NET Core microservice
FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS base
WORKDIR /app
EXPOSE 8080

FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY ["OrderService/OrderService.csproj", "OrderService/"]
RUN dotnet restore "OrderService/OrderService.csproj"
COPY . .
RUN dotnet build "OrderService/OrderService.csproj" -c Release -o /app/build

FROM build AS publish
RUN dotnet publish "OrderService/OrderService.csproj" -c Release -o /app/publish

FROM base AS final
WORKDIR /app
COPY --from=publish /app/publish .
ENTRYPOINT ["dotnet", "OrderService.dll"]
📚 Key Terms Summary

Monolith: A single deployable application containing all features. Simple to start, harder to scale independently at the component level.

Microservice: A small, independently deployable service that does one thing well and communicates with other services over a network.

IHttpClientFactory: The recommended .NET interface for creating HttpClient instances. Prevents socket exhaustion and integrates with DI.

Polly: A .NET resilience library for adding retry policies, circuit breakers, and timeouts to HTTP calls.

Message Queue: A persistent buffer for asynchronous service-to-service communication. One service publishes an event; another consumes it independently.

Eventual Consistency: In a distributed system, data across services will converge to the same value — but not necessarily instantly.

Chapter Summary

  • A monolith is a single deployable unit; microservices split the application into independently deployable services that communicate over a network.
  • Microservices offer independent deployment, scaling, and fault isolation — but add significant operational complexity. Start with a monolith and extract services when needed.
  • Use IHttpClientFactory (never new HttpClient()) for typed HTTP clients that communicate with other services.
  • Polly adds resilience: retry with back-off, circuit breakers, and timeouts protect your service from cascading failures.
  • Message queues (RabbitMQ, Azure Service Bus) enable asynchronous communication between services — one service publishes, another consumes, without blocking.
  • Microservices introduce distributed tracing, eventual consistency, network failure handling, and heavy operational overhead — weigh these costs against the benefits.
  • Docker containers make each microservice portable and consistently deployable across environments.
