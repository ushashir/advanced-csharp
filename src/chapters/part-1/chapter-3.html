Part 1 · Chapter 3

Encapsulation — Private Property

The art of hiding what should be hidden, and only showing what the world needs to see. Encapsulation is the safety lock that keeps your objects working correctly.

What you'll learn in this chapter

  • What encapsulation means and why it matters
  • The four access modifiers: public, private, protected, internal
  • Private fields with public properties
  • Adding validation logic inside property setters
  • A complete BankAccount class — a classic encapsulation example
  • The principle of "least privilege"

The Bank Vault

Imagine you walk into a bank to deposit some money. You hand the cash to the teller. The teller records the transaction, checks it is valid, and updates the balance. You do not walk behind the counter, open the vault yourself, and shove the money in. The vault is locked. Only the bank's internal processes can touch what is inside it. You interact through a controlled, safe interface — the teller window.

That is encapsulation. Your object's internal data is the vault. Your public methods and properties are the teller windows. The outside world interacts only through those controlled channels.

🏦 The Bank Vault Analogy

A BankAccount object holds a balance. That balance is the money in the vault. No one outside the class should be able to set the balance to any arbitrary number — that would allow fraud. Instead, you provide Deposit() and Withdraw() methods — controlled teller windows — that validate every transaction before touching the balance.

Encapsulation = hide the data, control the access.

The Problem Without Encapsulation

Let's see what happens when we don't encapsulate. Suppose we naively write: 

public class BankAccount
{
    public double Balance;  // public field — anyone can change it!
}

var account = new BankAccount();
account.Balance = 1000000;   // Works! Anyone can set any value
account.Balance = -99999;   // Also works! Negative balance — fraud!

Nothing stops someone from setting a negative balance, adding a billion pounds directly, or bypassing the transaction logic entirely. The class has no defence. This is a data integrity disaster.

Access Modifiers

C# provides four main access modifiers that control who can see and use a class member:

  • public — accessible from anywhere. Any code that can see the class can use this member.
  • private — accessible only within the same class. Not visible to any outside code, not even subclasses.
  • protected — accessible within the same class and in derived (child) classes. Not visible to completely unrelated code.
  • internal — accessible within the same assembly (project/DLL), but not from other assemblies. Useful for hiding implementation details from external packages.
Modifier Same Class Derived Class Same Assembly Everywhere ────────────────────────────────────────────────────────────────────── private ✓ ✗ ✗ ✗ protected ✓ ✓ ✗ ✗ internal ✓ ✗ ✓ ✗ public ✓ ✓ ✓ ✓
💡 The Principle of Least Privilege

Always give a member the most restrictive access modifier that still lets the code work. Make things private by default. Only widen the access when you have a specific reason to. This minimises the surface area where bugs can enter and makes your code easier to refactor later.

The BankAccount Class — Done Right

Now let's build the BankAccount properly. The balance is private. All access goes through controlled methods. 

public class BankAccount
{
    // Private field — no one outside can touch this directly
    private double _balance;

    // Public read-only property — outsiders can READ but not SET
    public double Balance => _balance;

    public string Owner { get; }

    public BankAccount(string owner, double initialDeposit = 0)
    {
        Owner = owner;
        if (initialDeposit < 0)
            throw new ArgumentException("Initial deposit cannot be negative.");
        _balance = initialDeposit;
    }

    // Controlled deposit method
    public void Deposit(double amount)
    {
        if (amount <= 0)
            throw new ArgumentException("Deposit amount must be positive.");

        _balance += amount;
        Console.WriteLine($"Deposited £{amount:N2}. New balance: £{_balance:N2}");
    }

    // Controlled withdrawal method
    public bool Withdraw(double amount)
    {
        if (amount <= 0)
            throw new ArgumentException("Withdrawal amount must be positive.");

        if (amount > _balance)
        {
            Console.WriteLine("Insufficient funds.");
            return false;
        }

        _balance -= amount;
        Console.WriteLine($"Withdrew £{amount:N2}. New balance: £{_balance:N2}");
        return true;
    }

    public override string ToString() =>
        $"{Owner}'s account — Balance: £{_balance:N2}";
}

Now let's use it:

var account = new BankAccount("Ada Lovelace", 500);

account.Deposit(250);
// Deposited £250.00. New balance: £750.00

account.Withdraw(100);
// Withdrew £100.00. New balance: £650.00

account.Withdraw(1000);
// Insufficient funds.

// This would cause a compile error — Balance has no setter!
// account.Balance = 999999;  // Error: property is read-only

Console.WriteLine(account); // Ada Lovelace's account — Balance: £650.00

Property Setters with Validation

Sometimes you want outside code to be able to set a property, but only with valid values. You can add validation logic directly inside a property's set accessor: 

public class Person
{
    private int _age;

    public string Name { get; set; }

    public int Age
    {
        get => _age;
        set
        {
            if (value < 0 || value > 150)
                throw new ArgumentOutOfRangeException("Age must be between 0 and 150.");
            _age = value;
        }
    }

    public Person(string name, int age)
    {
        Name = name;
        Age = age;  // Goes through the setter validation
    }
}

var p = new Person("Grace Hopper", 85);
p.Age = 86;   // Fine
p.Age = -5;   // Throws ArgumentOutOfRangeException

Notice the keyword value inside the setter — it automatically refers to whatever the caller is trying to assign. This is a C# built-in contextual keyword for property setters.

Init-Only Properties (C# 9+)

Sometimes you want a property that can be set when the object is first created (via object initialiser) but never changed afterwards. C# 9 introduced the init accessor for exactly this: 

public class Customer
{
    public string Name { get; init; }   // can set at init, but not later
    public string Email { get; init; }
}

var customer = new Customer { Name = "Alan Turing", Email = "alan@example.com" };

// customer.Name = "Someone else";  // Compile error! init-only property

This is perfect for creating immutable (unchangeable after creation) objects. It's one of the features that makes C# great for building safe, predictable data models.

🔒 Records — The Ultimate Immutable Type

C# 9 also introduced records — a special type designed for immutable data. A record automatically gives you a constructor, properties, equality comparison, and a ToString() — all in one line: 

public record Point(double X, double Y);

We won't go deep into records in this chapter, but they are a powerful example of how C# uses encapsulation principles to enforce immutability at the language level.

Access Modifiers in Practice — Quick Reference

public class Example
{
    public string PublicProp { get; set; }       // Accessible everywhere
    private string _privateProp;                  // Only inside this class
    protected string ProtectedProp { get; }      // This class + subclasses
    internal string InternalProp { get; set; }   // Same assembly only

    public string ReadOnly { get; private set; } // Read publicly, set privately
}

The last one — { get; private set; } — is extremely common in C#. It lets outside code read the value but prevents outside code from changing it. Only the class itself can call the setter.

⚠️ Common Mistake: Auto-Property with No Restriction

A very common beginner mistake is to make every property public string X { get; set; } without thinking about whether the setter should be accessible. Before making a setter public, ask yourself: "Should outside code be allowed to set this directly? Or should they go through a method that validates the change?" If in doubt, start with private set and widen it only if needed.

📚 Key Terms

Encapsulation: The OOP principle of hiding internal data and only exposing controlled access points (methods/properties).

Access modifier: A keyword (public, private, protected, internal) that controls the visibility of a class member.

private: Only the same class can access this member.

public: Any code anywhere can access this member.

protected: The same class and all derived (child) classes can access this member.

internal: Any code within the same assembly (project) can access this member.

value keyword: Inside a property setter, value refers to the value being assigned.

init accessor: Like set, but only usable during object initialisation. Creates effectively immutable properties.

Chapter Summary

  • Encapsulation means hiding data inside a class and controlling access through public methods and properties.
  • Always prefer private fields; expose data through public properties or methods.
  • C# has four access modifiers: public, private, protected, internal.
  • Property setters can contain validation logic to ensure only valid values are stored.
  • { get; private set; } is a common pattern for properties that should be read publicly but set internally.
  • init-only properties (C# 9+) allow setting during object creation but prevent changes afterwards.
  • The Principle of Least Privilege: give members the most restrictive access that still works.
