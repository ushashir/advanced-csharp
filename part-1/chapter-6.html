Abstraction — The Steering Wheel

You drive a car without knowing how the engine works. That's abstraction — hiding the complex machinery and exposing only what's needed. Abstract classes make this principle part of your code's structure.

What you'll learn in this chapter

  • What abstraction means as an OOP principle
  • abstract classes — can't be instantiated, define a contract
  • abstract methods — declared but not implemented in the base class
  • Why abstract classes are different from regular base classes
  • When to choose abstract classes vs concrete base classes
  • A complete Shape hierarchy using abstraction

The Steering Wheel

You drive a car every day. When you want to turn left, you turn the steering wheel left. You do not think about the rack-and-pinion steering system, the power steering pump, the tie rods, or the wheel bearings. You just turn the wheel and the car turns. The complexity of how turning works is hidden away. You interact with a simple, clean interface — the steering wheel.

That is abstraction. The underlying complexity exists, but it is hidden. You are only shown what you need to know.

🚗 The Steering Wheel Analogy

An abstract class is like the specification for a steering wheel. It says: "Every vehicle must have a way to steer. The steering wheel is how you interact with it." It does not say how steering is implemented — a racing car and a truck both have steering wheels, but the mechanisms inside are completely different. Each concrete (non-abstract) subclass provides its own implementation of the steering mechanism.

The abstract class defines what must exist. Concrete subclasses define how.

Abstract Classes in C#

In C#, you declare an abstract class with the abstract keyword. An abstract class:

  • Cannot be instantiated directly — you cannot do new Shape().
  • Can (and often does) have abstract methods that subclasses must implement.
  • Can also have regular, non-abstract methods with a full implementation.
  • Can have constructors, properties, and fields — just like a regular class.
public abstract class Shape
{
    // Regular property — shared by all shapes
    public string Colour { get; set; }

    protected Shape(string colour)
    {
        Colour = colour;
    }

    // Abstract methods — no body here, subclasses MUST implement these
    public abstract double Area();
    public abstract double Perimeter();

    // Concrete method — default behaviour, available to all subclasses
    public void Describe()
    {
        Console.WriteLine(
            $"{Colour} {GetType().Name}: Area={Area():F2}, Perimeter={Perimeter():F2}");
    }
}

The abstract methods Area() and Perimeter() have no body — no curly braces, no implementation. They are just declarations: "I promise that every Shape will have these methods." The concrete subclasses will provide the implementation.

⚠️ You Cannot Instantiate an Abstract Class

This is a compile-time error: 

var shape = new Shape("red"); // Compile error! Cannot create abstract class

An abstract class is a concept, not a thing. You cannot have a "shape" in real life without it being a circle, a rectangle, a triangle, or something specific. The abstract class models that concept perfectly.

Implementing Abstract Methods — Circle and Rectangle

Every class that inherits from an abstract class must implement all abstract methods, or it must also be declared abstract. Here are two concrete shapes: 

public class Circle : Shape
{
    public double Radius { get; }

    public Circle(double radius, string colour = "red")
        : base(colour)
    {
        Radius = radius;
    }

    public override double Area() => Math.PI * Radius * Radius;
    public override double Perimeter() => 2 * Math.PI * Radius;
}

public class Rectangle : Shape
{
    public double Width { get; }
    public double Height { get; }

    public Rectangle(double width, double height, string colour = "blue")
        : base(colour)
    {
        Width = width;
        Height = height;
    }

    public override double Area() => Width * Height;
    public override double Perimeter() => 2 * (Width + Height);
}

public class Triangle : Shape
{
    public double A { get; }
    public double B { get; }
    public double C { get; }
    private double BaseLength { get; }
    private double HeightLength { get; }

    public Triangle(double a, double b, double c, double baseLen, double heightLen,
                   string colour = "green") : base(colour)
    {
        A = a; B = b; C = c;
        BaseLength = baseLen;
        HeightLength = heightLen;
    }

    public override double Area() => 0.5 * BaseLength * HeightLength;
    public override double Perimeter() => A + B + C;
}

Using the Hierarchy Polymorphically

Now the beautiful part — all three shape types are used through the abstract base class: 

using System.Collections.Generic;

var shapes = new List<Shape>
{
    new Circle(5, "red"),
    new Rectangle(4, 6, "blue"),
    new Triangle(3, 4, 5, 3, 4, "green"),
    new Circle(2.5, "purple"),
};

foreach (Shape shape in shapes)
{
    shape.Describe();
}
Console.WriteLine();

// Find the largest shape
Shape largest = shapes[0];
foreach (var s in shapes)
    if (s.Area() > largest.Area()) largest = s;

Console.WriteLine($"Largest: {largest.GetType().Name} with area {largest.Area():F2}");

Output:

red Circle: Area=78.54, Perimeter=31.42
blue Rectangle: Area=24.00, Perimeter=20.00
green Triangle: Area=6.00, Perimeter=12.00
purple Circle: Area=19.63, Perimeter=15.71

Largest: red Circle with area 78.54

Abstract vs Concrete Base Classes

When should you use an abstract class rather than a regular (concrete) base class? Here are the guiding questions:

Use ABSTRACT class when: Use CONCRETE base class when: ───────────────────────────────────── ────────────────────────────────────── The concept cannot exist alone The base class is usable on its own ("Shape" without specifics = nonsense) ("Animal" with default behaviour = OK) Subclasses MUST provide their own Subclasses can optionally override implementation of key methods but the base version is acceptable You want to enforce a contract You want to provide shared behaviour ("all shapes MUST have Area()") that subclasses can override if needed
💡 Abstract Class vs Interface

In Chapter 10 we will cover interfaces, which are C#'s other tool for defining contracts. For now, the key distinction:

  • An abstract class can have both abstract methods (no body) and concrete methods (with body). It represents an "is-a" relationship. A Circle IS A Shape.
  • An interface defines a contract with no implementation (traditionally). A class can implement multiple interfaces. Use it for "can-do" relationships: a Circle CAN BE drawn, CAN BE serialised.

Abstract Methods Must Be Overridden

If you inherit from an abstract class and don't implement all its abstract methods, you get a compile error. The class must either implement them or also be declared abstract: 

// This compiles fine — implements both abstract methods
public class Square : Shape
{
    public double Side { get; }
    public Square(double side) : base("yellow") => Side = side;
    public override double Area() => Side * Side;
    public override double Perimeter() => 4 * Side;
}

// This does NOT compile — missing Area() and Perimeter()
// public class Hexagon : Shape { }  // Error: must implement abstract members

// This compiles — but Hexagon itself is abstract (still must be subclassed)
public abstract class Hexagon : Shape
{
    protected Hexagon(string colour) : base(colour) { }
    // Still abstract — postpones implementation to further subclasses
}

Abstract Properties

Properties can also be abstract — not just methods: 

public abstract class Employee
{
    public string Name { get; set; }

    // Abstract property — subclasses must provide get (and optionally set)
    public abstract decimal MonthlySalary { get; }

    public void PrintPayslip()
    {
        Console.WriteLine($"{Name}: £{MonthlySalary:N2}/month");
    }
}

public class SalariedEmployee : Employee
{
    public decimal AnnualSalary { get; set; }
    public override decimal MonthlySalary => AnnualSalary / 12;
}

public class HourlyEmployee : Employee
{
    public decimal HourlyRate { get; set; }
    public int HoursPerMonth { get; set; }
    public override decimal MonthlySalary => HourlyRate * HoursPerMonth;
}

// Usage
var employees = new List<Employee>
{
    new SalariedEmployee { Name = "Alice", AnnualSalary = 60000 },
    new HourlyEmployee { Name = "Bob", HourlyRate = 25, HoursPerMonth = 160 },
};

foreach (var emp in employees)
    emp.PrintPayslip();
// Alice: £5,000.00/month
// Bob: £4,000.00/month
🏗️ The Template Method Pattern

What you just saw — an abstract class with a concrete method (PrintPayslip) that calls an abstract method (MonthlySalary) — is a famous design pattern called the Template Method Pattern.

The abstract class defines the skeleton of an algorithm in a concrete method, leaving some steps to be filled in by subclasses. The overall structure stays the same; only the variable parts change. It is one of the most elegant uses of abstraction.

📚 Key Terms

Abstraction: The OOP principle of hiding complexity and exposing only the essential interface. Show the steering wheel, not the engine.

abstract class: A class that cannot be instantiated. Used as a base class that defines a partial implementation and forces subclasses to complete it.

abstract method/property: Declared but not implemented in the abstract class. Subclasses that are not abstract must override it.

Concrete class: A non-abstract class. Can be instantiated. Must implement all abstract members it inherits.

Contract: The set of methods/properties that an abstract class (or interface) requires subclasses to implement.

Template Method Pattern: A design pattern where an abstract class defines the overall algorithm, and subclasses provide the variable steps.

Chapter Summary

  • Abstraction hides complexity and exposes only what users of the class need to know.
  • An abstract class cannot be instantiated — it defines a contract that subclasses must fulfil.
  • Abstract methods have no body; subclasses must override them with an implementation.
  • Abstract classes can also have concrete (non-abstract) methods with full implementations.
  • If you inherit from an abstract class without implementing all abstract members, your class must also be declared abstract.
  • Abstract properties work the same way as abstract methods — subclasses must provide the getter (and optionally setter).
  • The Template Method Pattern uses a concrete method in an abstract class that calls abstract methods to be filled in by subclasses.
